# 项目介入前的架构地图

## 2026-09-16 · 前端项目全局理解先于局部改动

- ID：`frontend-project-architecture-discovery`；状态：`candidate`。
- Owner：周启明 · 体验工程官（Frontend Engineer）；review：自审；confidence：medium（用户明确要求，待真实项目复核）。
- 触发：首次介入陌生前端项目，或改动会触及页面结构、路由、通用组件、共享状态、请求层、样式体系、构建或测试约定。
- 决策：实现前先建立最小架构地图：确认框架与启动入口；追踪目标路由及其 layout；定位组件库、设计令牌和局部样式边界；识别共享状态、请求/缓存、鉴权与错误处理；检查构建、测试、lint 和项目约定。只读取与目标变更相连的链路，不为“熟悉项目”全库加载。
- 输出：在任务简报中写明受影响入口、可复用组件/逻辑、不可破坏约束、未确认项及相称的验收路径。发现现有组件或通用逻辑已覆盖需求时优先复用；确有边界缺口再新增抽象。
- 采用例：新增筛选页前先确认现有路由壳、搜索组件、请求状态模型和 CSS Modules 约束，再在既有边界内实现。
- 拒绝例：只打开目标页面就复制一套表单、请求封装或全局样式，随后才发现项目已有等价组件、缓存约定或权限入口。
- 适用边界：架构地图是实施前的定向理解，不替代业务需求、接口契约、Figma 实例、无障碍验收或真实运行验证；未读到的区域应标 unknown，不臆测项目规范。
- 复核触发：下一次跨页面或跨模块前端任务，检查该地图是否减少重复组件、回归和返工；出现架构事实与地图不符时停止复用并修订。
