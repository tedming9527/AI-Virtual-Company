# 页面状态验证：受控 Debug、稳定逻辑与关键旅程

- ID：`frontend-page-state-validation`
- Owner：`frontend-expert`
- 内容类型：`method_template`
- 状态：`candidate`
- 证据：本模板无实测、独立评审或生产收益证据；以下示例为假设，不是历史运行记录。

## 触发

页面有大量 loading/empty/error、角色、活动、订单或容器状态，视觉快速调整且页面 DOM 测试维护成本上升。

## 分层验证

1. 开发/受控测试环境以显式入口切换 ViewModel/fixture，观察视觉、布局、文案、按钮与组合状态。入口名称由项目配置。
2. 单元测试保护稳定规则：入口决策、字段转换、权限、跳转参数、请求归属、埋点 payload 等脱离 DOM 仍成立的规则。
3. 页面/端到端只守高代价跨层旅程：授权、支付、预约、防重复提交与关键状态流转。

先判断断言保护的契约与失败风险。普通文案、CSS 类、组件库 DOM、文件存在或易变布局通常由受控状态探索验收；若涉及关键行为/可访问性/公共结构契约，应保留相称检查，不一刀切删除。

## 实施护栏

- Debug 默认不进入生产；线上诊断需内部身份与环境门禁，公开 URL 参数不构成权限。
- 只替换读取状态或注入无副作用 adapter；支付、领取、提交、删除、埋点等真实副作用默认禁用。
- fixture 与单测共享受审事实源，关闭 Debug 后不留 mock、缓存或全局副作用，真实模式是默认路径。
- jsdom 不证明视口、滚动、安全区、Portal、WebView/桥接和视觉；在目标浏览器/容器验收。
- 状态浮板不证明业务规则、竞态、后端授权与副作用，稳定逻辑与服务端测试仍需保留。

## 假设示例与反例

应采用：多状态活动页在真实移动视口切换 fixture；入口动作与跳转参数保留纯逻辑测试，一条主旅程做端到端。

不应采用：Debug 直接真实支付，再以人工观感替代 requestId、金额转换、防重复和回调验收；使用假 transport 并保留关键契约测试。

## 复核

当前入口与生产隔离须逐项目核对。记录状态漏项、人工切换时间、测试维护与返工，测试数量变化不独自证明收益。fixture 漂移、安全暴露或关键回归漏检时停止采用并修订。

本方法不扩大当前用户授权；结论仅限本次实际取得的证据层。
