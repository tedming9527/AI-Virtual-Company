## 1. P0 问题与会改变的具体决策

**问题：**当下游既不接受幂等键，也没有机器可用的终态查询时，哪些业务仍可按受限语义执行，哪些必须阻断？

它会改变四项具体决策：是否允许接入该下游；超时后能否自动重试；是否需要持久意图、人工确认或补偿；发布状态是“受限可用”还是 `blocked`。事实所有者包括下游接口维护者、业务/财务/运营风险责任人、实现负责人和质量复核人。禁止为研究制造真实扣款、履约、权益或删除副作用，也禁止用本地锁、业务键、outbox 或队列宣称远端 exactly-once。

| 类型 | 证据与边界 |
|---|---|

| 协议标准 | [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)规定：非幂等请求除非能确认其语义实际幂等，或能确认原请求从未生效，否则客户端不应自动重试；代理不得自动重试非幂等请求。 |
| 官方可靠性资料 | AWS 的[安全重试文章](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)以“请求超时但资源可能已创建”为例说明盲重试会产生第二个副作用；[重试门禁](https://docs.aws.amazon.com/wellarchitected/2023-04-10/framework/rel_mitigate_interaction_failure_limit_retries.html)要求先验证服务幂等再实施重试。 |
| 官方模式边界 | AWS [Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)只解决本地数据库与消息发布的双写问题，并明确消息可能重复、消费者仍须幂等。因此 outbox 会提高“意图被再次投递”的可靠性，却不能让非幂等下游安全。 |
| 补偿与人工 | Azure [Compensating Transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)指出补偿是业务特定、会失败且步骤应幂等；高影响或歧义决策应暂停并引入人工，部分不可逆步骤必须在关键校验后才执行。 |
| 第一方契约对照 | Stripe [Idempotent requests](https://docs.stripe.com/api/idempotent_requests)和 PayPal [Idempotency](https://developer.paypal.com/reference/guidelines/idempotency/)都把幂等键用于连接错误或不明确响应后的安全重试。它们只证明成熟支付契约如何关闭该风险，不能证明当前未知下游具备同等能力。 |
| 冲突 | 既有迁移材料曾把 outbox 与自动恢复写得过于普遍；上一轮质量复核已将其收窄为“确需异步可靠投递时才采用”。本轮官方 outbox 资料进一步证明，非幂等消费者会使可靠重放变成重复副作用风险。 |
| Unknown | 当前没有具体下游、调用方法、SDK/代理/消息中间件重试配置、人工后台、撤销接口、业务损失上限、事实所有者或沙箱行为。 |
| 陈旧/不适用 | 2026-09-10 日期纯函数 9/9 历史运行与本题无跨系统证明力；H2、Mock、结构检查和旧训练题均不能解除真实发布门禁。 |

## 3. 专业研究结论及来源

**结论：不能按行业名称一刀切；应按“歧义能否关闭、重复/遗漏是否可接受、动作是否可逆、影响是否高风险”判定。** 在本题前提下，自动安全重试没有成立条件；最多只能选择一次尝试、业务明确接受的有限重复，或人工门禁。判定矩阵如下：

| 业务条件 | 允许模式 | 必须保留的终态 | 决策 |
|---|---|---|---|
| 重复与遗漏都在事实所有者书面接受的低影响范围内 | 单次或明确上限的 best-effort；禁止把接受回执写成业务成功 | `Attempted/Unknown`，可按约定自然过期 | **受限允许** |
| 重复不可接受、遗漏可接受，且没有隐藏重试层 | 只允许一次客户端尝试；SDK、代理、队列和任务调度均关闭自动重试 | 超时为 `Unknown`，不得补发 | **受限允许** |
| 高影响，但存在独立人工证据（下游后台、对账单、支持确认）和经验证的补偿 | 一次尝试后冻结；先人工确认，再决定补偿或新业务操作 | `ManualHold → Confirmed/Compensated` | **仅人工门禁允许** |
| 金额、不可逆履约、唯一权益、法律/身份状态或破坏性动作；重复或遗漏任一不可接受，且无独立确认 | 不调用真实下游 | `Blocked` | **必须阻断** |
| 业务要求最终完成或“恰好一次”，但下游无幂等、无查询、无独立确认 | 本地任何重试、锁、outbox、fencing 均不能满足 | `CapabilityMissing` | **必须阻断并要求改契约/换供应商** |

这里的“一次尝试”只是本方策略，不等于远端 at-most-once 保证；必须核对 SDK、服务网格、网关、代理、消息系统和人工补提是否会重放。若动作经契约证明天然幂等，或能证明原请求未生效，则已脱离本题前提，应重新分类，而不是偷换为“无幂等也安全”。

## 4. 竞争假设与反例分析

**H1：所有无幂等、无查询的跨系统写入都应阻断。** 这能避免高风险重复，但会把“遗漏和重复均可接受的低影响 best-effort 通知”也一并禁止。RFC 只禁止在缺少判定能力时自动重试非幂等请求，并未禁止所有首次调用；AWS 也强调严格幂等契约的复杂度并非适合所有场景。**判定：过度保守，不作为统一规则。**

**H2：按重复损失、遗漏损失、可逆性和独立确认能力分级；低影响可受限执行，高影响歧义则阻断。** 它能解释为何礼貌提醒可以单次 best-effort，而付款、发货、唯一权益不能在同样能力下放行。反例是“看似低影响的通知”若承担法定送达、账号安全或合同生效含义，遗漏就不再可接受，必须升级为阻断或更换有回执能力的通道。**判定：采用，但必须由事实所有者签核风险分类。**

**H3：本地 outbox、唯一业务键和单 worker 能弥补下游缺失。** 反例：outbox relay 在发布后、标记完成前宕机会再次投递；AWS 官方也要求消费者幂等。单 worker 或租约只限制本地并发，无法撤销已抵达下游的第一次调用。**判定：拒绝。** outbox 仅在需要可靠保存投递意图时使用，并会把下游非幂等暴露得更明显。

## 5. 三条可立即采用的行动规则

1. **先做能力门禁，再选恢复机制。** 对每个副作用记录 `supportsIdempotency / supportsTerminalQuery / hasIndependentEvidence / isCompensable / duplicateTolerance / omissionTolerance`；前三项证据不足时不得开启自动重试。
2. **枚举所有重试源。** HTTP 客户端、SDK、服务网格、代理、消息 broker、定时任务、人工按钮分别核对；非幂等 unknown 路径默认全部关闭，只有能证明原请求未生效或业务明确接受重复时才放开。
3. **Unknown 不是失败，更不是成功。** 保存请求摘要、单次尝试时间、连接阶段、可得远端引用和责任人；高影响 unknown 冻结后续副作用，无法取得独立证据时保持 blocked，不用“补偿一次”猜测原动作发生与否。

## 6. 未见迁移题及独立作答

**题目：**同一第三方网关提供“开通门禁权限”和“发送非关键到访提醒”两个 POST 接口，均无幂等键、无状态查询。网关超时后可能已执行。团队计划统一写 outbox 并重试三次，是否可行？

**作答：**不可统一处理。门禁权限是安全与身份状态，重复开通、遗漏开通和错误撤销均可能高影响；没有独立后台、查询或可验证补偿时必须阻断接入，要求供应商补幂等/查询契约或更换通道。非关键提醒只有在业务所有者明确接受少量遗漏与重复、文案不承担法定或安全通知、且用户界面不显示“已送达”时，才可受限执行；若重复比遗漏更坏，则只做一次客户端尝试并关闭所有隐藏重试，超时记 `Unknown`。若两者共用 outbox，relay 重放会放大门禁风险，因此应拆分策略；outbox 不能成为下游 exactly-once 的替身。

## 7. 最小真实验证协议

**输入：**一个明确目标下游及具体操作；当前官方契约/SDK版本；业务对象和稳定本地操作号；事实所有者签字的重复、遗漏、不可逆性与人工责任表；成功、明确拒绝、发送前失败、发送后响应丢失四类场景。

**环境与权限：**只用供应商官方 sandbox、隔离测试租户或经过批准且不会产生真实扣款/履约/权益的测试能力。若只有本地 stub，只能验证本方状态机和重试配置，不能证明真实下游行为。权限限于读取契约/日志和测试租户写入；禁止生产副作用。

**步骤：**

1. 契约审计：确认没有幂等键、资源查询、回调、独立后台记录或支持查询；若发现任一能力，重新分类问题。
2. 重试盘点：固定客户端、SDK、网格、代理、broker 和调度器版本，导出重试配置；通过调用计数证明非幂等路径不存在隐式自动重试。
3. 在 sandbox/隔离替身注入“未发送即失败”和“已接收但响应丢失”；前者只有在能证明未生效时才可再次尝试，后者必须进入 `Unknown` 且不再次调用。
4. 对低影响候选，分别模拟一次遗漏和一次重复，由事实所有者确认实际后果仍落在已签核范围；未签核不得用工程判断代替。
5. 对人工门禁候选，验证操作员能从独立第一方证据确认终态；只有确认原动作已发生后才演练补偿。补偿本身无幂等或无法确认时，不得自动化。
6. 由顾清妍复核“发送次数、远端测试记录、本地状态、人工证据”是否同层；任何只靠日志或本地锁的结论退回。

**必需证据：**版本化契约、风险签核、全重试层配置、脱敏 wire/SDK 日志、sandbox 远端记录、状态迁移审计、人工核对记录、补偿演练结果及复核结论。

**通过条件：**受限业务的重复与遗漏边界已由事实所有者确认；真实调用次数符合策略；发送后丢响应不会触发第二次副作用；高影响路径在能力缺失时确实被阻断；界面和批次汇总不把 Unknown 写成成功。

**阻断条件：**无法证明重试层已关闭；sandbox 与生产契约不一致；没有独立确认却要求最终完成；补偿依赖猜测；重复/遗漏损失或责任人未签核；任何测试可能触发真实资金、履约、权益或删除。

**退出方式：**停止新调用并禁用调度/relay；保留未决操作为 `Unknown/ManualHold`，不通过重试“清理”；撤销测试凭据，核对 sandbox 记录，按另行授权处理测试数据。

## 8. 适用、禁止套用与失效条件

- 适用：非幂等写接口、响应可能丢失、没有机器终态查询，且团队正在决定是否接入、重试或发布。
- 禁止套用：已被契约证明天然幂等、支持幂等键/终态查询/可靠回调的接口；纯本地事务；只读请求。它们应走各自更强的恢复方案。
- 禁止外推：不能因一次 sandbox 成功宣称生产 exactly-once；不能把人工后台当成自动查询 SLA；不能把“业务接受重复”解释为可以无限重试；不能用 outbox、FIFO、锁或 fencing 代替下游契约。
- 失效条件：下游版本、SDK/网格重试配置、业务风险、法规、补偿能力、人工证据渠道或责任人变化；发生任何无法用矩阵解释的重复/遗漏事故时立即重审。

## 9. 仍需真实任务关闭的 unknown

尚未知：目标下游到底是否完全没有幂等/查询/回调；POST 是否被 SDK、代理或人工流程重放；超时发生在发送前还是处理后；真实重复与遗漏损失；哪些动作不可逆；人工后台能否作为权威证据；补偿是否可重复、可确认；业务、财务、运营和安全谁有最终裁决权；允许的观察窗口和处理时限。上述事实不能由通用架构文献或本地状态推断关闭。

## 10. Skill、工具地图与检查清单建议

暂不创建或修改 Skill。建议把现有 `cross-system-terminal-review` 候选增加一个前置“下游能力门禁”，输出六项能力字段、所有重试源、受限执行/人工门禁/阻断结论和所需签核；该 Skill 只审查，不连接下游、不发送请求、不自动开启 outbox。

工具地图应登记：官方 API 契约与版本（只读）、SDK retry 配置（只读/本地测试）、服务网格和代理策略（只读）、消息 broker 投递语义（只读）、供应商 sandbox（有测试写副作用，需明确授权）、第一方后台/支持工单（可能含敏感数据，最小范围读取）。缺少目标契约时，不安装通用重试工具来掩盖能力缺口。

## 11. 停止理由与下一触发条件

**停止理由：**第一轮核对当前项目静态链路、上一轮报告和已复核知识，确认本地成功、afterCommit、锁和 outbox 均不能证明远端终态。第二轮核对 RFC、AWS、Azure、Stripe 与 PayPal 官方资料，新增了三项决定性证据：非幂等请求缺少“未执行证明”时不应自动重试；outbox 可能重复投递且仍依赖幂等消费者；高影响歧义应暂停并人工裁决。研究级矩阵已形成，但目标下游、真实契约、沙箱与风险签核不可得；继续扩读通用资料无法关闭这些项目事实，故以 `partial` 停止，不进入第三轮，不执行外部副作用。

**下一触发条件：**用户或项目提供一个具体下游、当前契约/SDK版本、测试租户、业务风险事实所有者和允许的测试范围。届时按第7节协议验证；若连续两轮仍拿不到新的真实契约或运行证据，再次停止并保持 blocked，不以更多设计文档替代事实。
