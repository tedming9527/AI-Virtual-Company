## 1. P0 问题与会改变的决策

**问题：高风险跨系统终态为 unknown 时，什么证据才能解除发布阻断？**

它会改变四个测试/验收决定：一笔操作能否从 `Unknown` 收口；界面能否显示成功；自动重试或补偿能否开启；包含该副作用路径的版本能否发布。事实所有者包括下游契约维护者、业务/财务/运营风险责任人、实现负责人、发布授权人和质量复核人。质量岗位负责判定证据是否命中主张，但不代填业务容忍度，也不代替发布授权。

禁止越界：案例、Mock、截图、构建、本地数据库或应用日志均不得单独证明远端副作用；不得为研究制造真实扣款、履约、权益、身份或删除；不得把“关闭一笔操作”外推为“版本能力已验证”。

## 3. 专项结论：关闭的是具体主张，不是一个词

**核心结论：高风险 `terminal unknown` 没有一张万能凭证。解除阻断需要一个与主张同层的证据包，同时满足权威性、关联性、语义、范围和时效；任何一项缺失，最多关闭部分 unknown。**

### 四类 Unknown 关闭矩阵

| Unknown | 要回答的主张 | 最低关闭证据 | 明确不足 | 关闭后的边界 |
|---|---|---|---|---|
| `existence` | 目标系统是否收到/执行过这次操作？ | 目标系统生成的操作/资源 ID、权威审计记录或查询结果，并与稳定业务键、账号/租户、请求摘要和时间窗关联；或由协议明确证明原请求从未被处理。 | 本地“已发送”、TCP/HTTP 客户端日志、队列 offset、`202 Accepted`、没有看到回调。 | 只说明动作存在或不存在；不说明业务是否成功或已终态。 |
| `semantics` | 状态码、回调类型、Pending/Success 到底代表什么？ | 当前版本的第一方契约/状态机、幂等与查询语义、终态枚举和一致性窗口；金额、SLA、可接受风险由业务事实所有者确认。 | SDK 类型名、Mock 约定、历史文档、开发者口头解释、签名有效但事件含义未核对。 | 只对该契约版本和业务口径成立；版本或口径变化即失效。 |
| `scope` | 证据能否覆盖拟发布的版本、环境、身份和场景？ | 目标构建/配置、账号/租户/区域、凭据权限、数据库 schema/约束、SDK/代理重试配置与测试记录可追溯；生产差异和未覆盖场景显式列出。 | “沙箱和生产应该一样”、本地 H2、单用户 happy path、旧版本截图。 | 只能解除证据实际覆盖范围；沙箱通过不等于生产副作用已验证。 |
| `terminal` | 最终业务副作用是什么，是否重复/遗漏？ | 目标系统权威当前状态查询；或经验证真实性且契约明确为终态的回调，再与远端资源核对；若无机器查询，则由授权事实所有者基于第一方结算单、履约账、后台记录完成可追溯人工对账。还须验证本地状态收敛且无额外副作用。 | 应用日志、单一回调、回调已签名、本地 DB `Success`、HTTP 2xx、补偿请求已发出。 | 可关闭一笔操作；除非同一机制在相称环境覆盖故障矩阵，否则不能证明版本恢复能力。 |

关闭记录至少包含：`claim_id / business_key / unknown_type / local_state / remote_reference / authority / contract_version / environment_identity / observed_at / terminal_state / evidence_refs / owner / reviewer / release_scope`。缺少稳定关联键时，多份证据也可能属于不同操作，不能拼成一个结论。

### 操作收口与发布解阻的两层判定

1. **单笔操作收口：**远端权威终态或可审计人工对账与本地状态一致，可把该笔从 `Unknown` 改为 `Succeeded / Rejected / Compensated`；不一致则转 `Conflict/ManualHold`，不是择一相信。
2. **高风险能力解阻：**必须在授权、相称环境覆盖成功、明确拒绝、发送前失败、目标已受理但响应丢失、重复/迟到回调、查询暂时不可用和本地提交失败等风险场景；每个场景均能以同一业务键得到权威终态、阻止盲重试并使本地收敛。再由事实所有者签核风险、发布人独立授权。
3. **范围隔离解阻：**若高风险路径在目标环境通过已验证的 feature flag、权限拒绝或路由隔离不可达，可以发布不包含该能力的其他范围；结论必须写“风险路径被隔离”，不能写“高风险能力已通过”。

因此，单个真实回执、一次对账或一个生产成功案例都不足以解除“机制能力”的发布阻断；反过来，也不应让一个已被证明不可达的高风险路径无限阻塞无关修复。

## 4. 竞争假设与反例

**H1：只要存在高风险 terminal unknown，整个版本一律阻断。** 该策略最保守，但反例是高风险退款入口已在目标环境被独立权限策略拒绝，待发布内容只是无副作用的文案修复。此时应阻断退款能力，不必阻断不可达的无关范围。**判定：拒绝“一刀切版本”，保留“可达风险路径必阻断”。**

**H2：按主张拆分 unknown；只有权威终态关闭，或风险路径被可验证隔离，才解除相应范围阻断。** 它同时保留真实风险和交付边界。反例压力测试：feature flag 只藏按钮，但 API、定时任务或旧客户端仍可调用，则隔离证据不成立，仍须 blocked。**判定：采用。**

**H3：签名回调或完整应用日志已足够。** 反例：PayPal 官方说明失败回调会重试，签名只能证明来源；Stripe 事件是发生时的资源快照。一个真实、已签名但迟到的 `processing` 事件不能推翻随后查询到的 `failed`，应用“只发送一次”日志也不能证明目标未执行。**判定：拒绝。** 日志用于关联和审计，回调用于提供候选事实，最终性取决于第一方契约和当前状态证据。

## 5. 三条立即采用的行动规则

1. **先写关闭主张，再收证。** 明确是关闭某笔 `existence`、解释状态 `semantics`、扩大覆盖 `scope`，还是证明 `terminal`；证据不能跨格升级。
2. **终态采用证据包，不采用单信号。** 高风险至少核对稳定业务键、目标权威事实、当前契约、环境身份、本地收敛和时间窗；签名、日志、DB 或截图单独出现只记过程证据。
3. **发布与终态分开裁决。** 未关闭的可达高风险路径保持 blocked；若通过目标环境证据证明路径不可达，可只放行隔离后的范围。质量给出证据结论，事实所有者决定风险口径，发布人独立授权。

## 6. 未见迁移题及独立作答

**题目：**仓储供应商的“购买运单”接口返回 `202 + jobId` 后连接中断。本地为 `Pending`，随后收到签名有效的 `label.created` 回调，但供应商查询接口仍显示 `processing`；重复购买会产生第二笔费用。团队想发布“立即重试”按钮，是否可以？

**作答：**不可以。`202/jobId` 和签名回调可帮助关闭存在性与来源真实性，但 `label.created` 是否代表已计费、可用运单或中间快照要由当前契约解释；权威查询仍为 `processing`，故终态未关闭。按钮若发起新请求会把 unknown 扩大为重复费用风险，应继续显示“处理中/需核对”，用同一业务键轮询权威状态或由授权人员核对供应商账单。只有查询确认原请求从未生效，或供应商契约支持同键幂等并返回原结果时，才可允许有限重试。若本次版本能在目标环境证明该写接口被权限/路由完全隔离，可发布其他无关内容，但不能宣称“购买运单链路通过”。

## 7. 最小真实验证协议

| 项目 | 最低协议 |
|---|---|
| 输入 | 一个具体高风险操作；稳定业务键与不可变请求摘要；当前下游契约/SDK版本；目标版本；业务所有者确认的重复、遗漏、不可逆性、观察窗口和责任人。 |
| 环境 | 供应商官方 sandbox、隔离测试租户或经批准的生产等价无真实价值环境；数据库、队列、SDK、代理和重试配置与拟发布版本可追溯。只有 stub/Mock 时停止在本方状态机验证。 |
| 权限 | 默认只读；测试写入只限授权测试对象，具备查询、回调验证和清理权限；禁止真实资金、履约、权益、身份或删除副作用。业务、下游、实现、质量和发布责任人明确。 |

| 阻断条件 | 无目标权威查询/对账；契约语义或生产差异不明；稳定键不能贯穿；任一隐藏重试不可控；回调无法验证或不能判终态；本地/远端冲突；事实所有者、观察窗口或发布范围未确认；测试可能触发真实高风险副作用。 |
| 退出方式 | 关闭测试写入口和所有调度/重试，保留未决操作为 `Unknown/ManualHold`；核对远端测试记录与本地记录，撤销测试权限并按授权清理。未确认终止时不得用补发或删记录“收口”。 |

本轮没有相称环境，以上是最低协议，不是已执行结果。

## 8. 适用、禁止套用与失效条件

- **适用：**支付、退款、履约、唯一权益、身份权限、库存扣减、不可逆写入，以及任何重复/遗漏后果较高的跨系统操作。
- **可降低：**纯只读、可安全复算、低影响且重复/遗漏均由事实所有者接受的操作，可减少人工签核，但仍不得把过程回执写成终态。
- **禁止套用：**不能因某供应商的幂等、回调或查询能力推断另一供应商；不能用一次 sandbox 成功宣称生产正确；不能把签名真实性、HTTP 2xx、outbox、锁、队列或本地唯一键写成远端终态。
- **失效条件：**下游契约、API/SDK、状态枚举、回调签名、账号/租户、区域、数据库 schema、重试配置、业务容忍度、观察窗口、隔离策略或发布范围任一变化时，旧关闭结论停止自动沿用。

## 9. 仍需真实任务关闭的 Unknown

当前没有目标下游及其事实所有者；未知请求是否被客户端、代理、broker 或人工流程重放；未知查询是强一致、最终一致还是历史快照；未知回调的顺序、重复、签名和终态含义；未知 sandbox 与生产差异；未知人工后台/结算单能否成为权威证据；未知可接受观察窗口与冲突升级 SLA；未知哪种隔离能覆盖 API、任务和旧客户端；未知本协议能否降低真实任务的误报通过、escaped defect 和 unknown 关闭时长。

## 10. Skill、工具地图与检查清单建议

暂不新建 Skill。建议先把现有 `claim-evidence-gate` 候选扩展为只读的 `unknown-closure-review` 检查表，强制输出：主张、unknown 类型、权威来源、稳定关联键、契约版本、环境身份、时间窗、本地/远端一致性、关闭范围、剩余冲突、事实所有者和发布授权。它只能审证，不能连接下游、发送请求、自动重试或把 `partial` 改成通过。

工具地图优先登记第一方能力：版本化 API 契约、资源/操作查询、回调签名验证、sandbox、审计/结算后台、SDK/网关重试配置、数据库查询和发布隔离读取。每项记录权限、数据去向、写副作用、保留期、是否能证明真实性/当前状态/终态。至少经历三个真实可比案例且字段稳定后，再评估做自动化证据包生成器；当前过早自动化会把未知语义固化。

## 11. 停止理由与下一触发条件

**停止理由：**第一轮核对当前项目静态失败模式、上一轮测试门禁、跨系统知识和内部化状态轴，确认本地日志、Mock、数据库与单次回调不能跨层解除发布阻断。第二轮核对 RFC、AWS、Stripe、PayPal 第一方资料，新增了三项决定性证据：非幂等重试必须有语义保证或“原请求未生效”证明；签名只关闭消息真实性；事件/回调与当前资源终态必须按供应商契约区分。四类 unknown 关闭矩阵、操作/发布双层判定和最低协议已形成，但具体下游、相称环境、真实回执与风险签核不可得。继续扩读通用资料不会关闭这些事实缺口，故两轮后以 `partial` 停止，不执行第三轮或外部副作用。

**下一触发条件：**真实任务提供具体下游、当前契约/SDK、授权隔离环境、稳定业务键、可查询或人工对账来源、业务事实所有者及拟发布范围。届时按第 7 节执行；若两轮仍没有新增真实契约或运行证据，保持 blocked，不用更多日志或案例替代。
