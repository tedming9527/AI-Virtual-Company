## 1. 路由判断

判断是否交给 JEV，先问“这是可枚举判断，还是生成”，再看事实在哪里、是否阻塞：

| 场景 | 路由 | 理由 |
| --- | --- | --- |
| 同一短状态已有于上下文，要判断分类、下一步和质量 | 一次批量 `jev_judge`，分别使用 `choice` / `noul` / `score` | 是可枚举判断；同状态必须批处理，避免逐题往返 |
| 大量记录已在文件或工具输出 | 脚本把数据管道给 `jev-use judge` CLI | 不把大块事实搬进主对话；数据与判定尽量留在会话外 |
| 一次性的高风险、不可逆动作，且事实已在上下文，动作被该判断阻塞 | `jev_gate` | 只 gate 这一项动作；`escalate` 后由主模型裁决 |
| 每次工具调用都需要重复安全门禁 | 一次配置 `jev-use hook gate` | 避免每步手工调用；门禁判断离开主对话 |
| 写说明、代码、开放式方案，或选项尚不能枚举 | 主模型负责 | JEV 不是生成器，也不能替代规划与写作 |

## 2. 真实批量 `jev_judge` 实操

### 合成反馈

- A：面对保存在文件中的 1,200 条合成记录，把全文复制进主对话后逐条调用 `jev_judge`。
- B：对同一短状态的三个判断一次批量提交 `noul` / `choice` / `score`，只执行非升级项。
- C：收到 `answer=continue`、`escalate=true`、`reason=unsure` 后，未复核就继续执行。

每次请求都在一个 MCP call 中批量提交同一组 9 题：对 A、B、C 各判断“分类、下一步、质量”。最初不可达调用使用 `confidence_threshold=0.95`；恢复后的有效调用使用 `0.75`。重试只修正连接/模型参数，没有改题；任何一次都未包含真实主体或内部数据。

### 调用链与有效调用元数据

| 次序 | 请求 | 客户端墙钟 | 结果与处置 |
| --- | --- | --- | --- |
| 1 | 未指定可用后端模型 | `12,265 ms` | 9/9 `unreachable`，后端 `unconfigured`；未设临时凭据、未切 mock，全部回交主模型 |
| 2 | 误把后端/模型组合写成 `typesafe/jev-1.13.0` | `17,456 ms` | HTTP 400 `Unknown model`；只修正参数，不改题、不改阈值、不追求特定答案 |
| 3 | 裸模型名 `jev-1.13.0` | `7,271 ms` | 有效语义批量完成；后端 `typesafe`，服务端延迟 `939 ms` |

有效调用的计量：`inputTokens=1,414`、`outputTokens=314`，共 9 个判断；`confidence_threshold=0.75`。客户端墙钟包含 MCP 往返和工具包装时间，不能与服务端 `latencyMs` 混写。

### 有效 verdict、置信度与升级处置

| ID | JEV answer | confidence | escalate | 主模型处置 |
| --- | --- | --- | --- | --- |
| `A_class` | `misrouted_bulk` | 1.00 | false | 采纳 |
| `A_next` | `pipe_cli` | 1.00 | false | 采纳 |
| `A_quality` | 0.82；分布 0:0.18、1:0.82、2:0 | 0.73 | **true / unsure** | 仅作先验；复核后定为 1/2“部分合格” |
| `B_class` | `correct_batch` | 0.99 | false | 采纳 |
| `B_next` | `retain_pattern` | 1.00 | false | 采纳 |
| `B_quality` | 1.89；分布 0:0.01、1:0.09、2:0.90 | 0.84 | false | 按最高权重等级采纳为 2/2 |
| `C_class` | `escalation_mishandled` | 1.00 | false | 采纳 |
| `C_next` | `main_model_review` | 1.00 | false | 采纳 |
| `C_quality` | 0；分布 0:1、1:0、2:0 | 1.00 | false | 采纳为 0/2 |

整合后的结论：

| 反馈 | 分类 | 下一步 | 质量 |
| --- | --- | --- | --- |
| A | `misrouted_bulk` | `pipe_cli`：由脚本把文件管道给 CLI，并批处理 | 1/2：有结果但方法低效；本项由主模型处理升级 |
| B | `correct_batch` | `retain_pattern`：保留同状态批量与升级回接 | 2/2：合格且边界清楚 |
| C | `escalation_mishandled` | `main_model_review`：暂停动作并由主模型重审 | 0/2：升级项被误当硬结论 |

### 质疑与修订

初看 A 已经“得到结果”，容易把质量直接判成合格；但路由规则同时要求文件数据留在脚本/CLI、同状态批处理。JEV 对 A 的质量只报 0.73 置信度并触发升级，说明离散等级边界确有不确定性。复核时保留其 0.82 原始先验，不把小数伪装成最终等级；依据“结果存在但方法低效”的等级说明，最终裁决为 1/2。

修订后的训练方法把三件事分开记录：JEV 原始 answer、阈值触发的 escalate、责任人最终裁决。以后即使答案看似合理，只要 `escalate=true` 就不能直接执行；修订不是重复调用直到通过，而是回到原始事实与预先冻结的等级定义。

`escalate=true` 的统一含义是“JEV 没有获得最终决定权”。`unsure` 时 `answer` 只能作先验提示；`unreachable` 时按 JEV 不存在处理；`writing/open_ended` 表示问题本就属于主模型；`oversized` 表示应压缩状态或改走文件/CLI 路由。

## 3. 使用 JEV 与不使用 JEV 的对照

对照对象固定为上述 A/B/C 的 9 个判断，避免换题造成伪比较。

| 维度 | 使用 JEV 的本次实测 | 不使用 JEV、由主模型直接判断 |
| --- | --- | --- |
| 耗时 | 有效调用服务端 `939 ms`，客户端端到端 `7,271 ms`；早先 unconfigured 为 `12,265 ms` | 主模型推理墙钟无独立计时接口，记 `unknown`，不伪造速度比较 |
| 主对话上下文占用 | `1,414` 输入 tokens、`314` 输出 tokens，且 state 与 verdict 都进入主对话；这是费率/延迟实验，不是 token 节省 | 未提供独立 token 计量；读取同一压缩状态并直接产出短结论，仍占主模型推理上下文 |
| 输出一致性 | 与人工基线的 6 个分类/下一步完全一致；3 个质量分数映射到离散等级后也一致，A 因阈值升级后由主模型确认 | 人工基线为 A=1、B=2、C=0；有 JEV 结果后得到同样最终等级 |
| 升级处理 | 有效调用 1/9 升级；保留 0.82 先验但不直接执行，由主模型裁决 | 先前 unreachable 为 9/9 回交；人工基线直接由主模型负责并标明来源 |
| 适用边界 | 后端在线、问题可枚举、状态足够小且批量时最有价值；文件大批量应改 CLI | JEV 不可用、生成任务、开放式推理、敏感数据或选项不能枚举时使用 |

结论：同题语义结果与人工基线一致，且有效批量服务端延迟可测为 939 ms；但主模型基线无独立墙钟/token 计量，所以不能声称端到端提速或 token 节省。案例一致不等于生产准确率或长期提效。

## 4. 脱离 JEV 后模拟其高效模式

JEV 不可用时，不模拟它的“答案”，只复用它约束判断的工作方式：

1. **状态压缩**：只保留决定所需事实、目标和边界；文件内容保留在文件中，用引用或脚本处理，禁止整块搬进主对话。
2. **问题类型化**：真假概率用 `noul`，互斥下一步用 `choice`，有序质量档位用 `score`；开放式写作留给主模型。
3. **预先枚举**：在看答案前列出互斥选项或有序等级，避免裁决时临时改标准。
4. **按状态批处理**：同一 state 的全部判断组成一个数组，一次处理；不同事实域分批，避免超大 state。
5. **设置信心阈值**：按错误代价定阈值；高风险动作阈值更高。没有校准数据时只把阈值当升级规则，不伪装成真实概率。
6. **统一升级队列**：低于阈值、事实冲突、选项不全、状态过大或执行器不可达时，写入 `escalate` 队列，由主模型结合原始证据复核。
7. **来源标注**：最终表格为每项保留 `answer / confidence(or unknown) / escalate / reason / owner`，避免把先验、机器判断和主模型结论混写。

可执行的无 JEV 模板：

```text
state := 最小充分事实 + 目标 + 禁止范围
questions := 同一 state 下的 [{id, type, options|levels, question}]
for question in questions (single batch):
  answer := 按预先枚举标准判断
  confidence := 有校准依据则填写，否则 unknown
  if 证据不足 or 选项不全 or 高风险且把握不足:
    escalate := true; owner := 主模型/责任人
  else:
    escalate := false; owner := 当前裁决者
```

这种方法减少来回切换并提高可审计性，但不会获得 JEV 的独立判断、定价或延迟优势。

## 5. 未预先给答案的迁移题

### 冻结题面

CI 产生了 8,000 行合成日志，日志只存在文件中。需要判断四件事：构建是否成功、失败类别、严重度等级、下一步操作；随后要写一段发布说明。另有一次不可逆清理动作，只有安全判断通过后才能执行。请路由每个步骤，并说明任何返回 `escalate=true` 时怎么办。

题面冻结时未附标准答案；先完成初答，再依据已加载的 JEV 规则质疑和修订。

### 初答

- 四项日志判断由脚本把文件管道给 `jev-use judge` CLI，一次批量完成。
- 发布说明由主模型写，不交给 JEV。
- 不可逆清理动作使用一次性 `jev_gate`；若升级则停止清理并由主模型复核。

### 质疑与修订

初答遗漏了两个路由条件：清理安全事实若仍只在文件里，应该先由脚本/CLI 判断，不能为了 `jev_gate` 把大日志搬进上下文；若安全门禁会重复覆盖每次工具调用，则应一次配置 hook gate，而不是反复手工调用。

修订结论：日志中的四项判断留在脚本/CLI 且批处理；发布说明由主模型生成；一次性清理只有在“最小安全事实已在上下文”时使用 `jev_gate`，事实仍在文件则继续走 CLI；重复全链路安全门禁改用 hook gate。任何 `escalate=true` 都暂停相应动作并回交主模型，`unreachable` 时不绕过。题面和初答均在有效 JEV 结果之外独立冻结，没有把标准答案预载为题目事实。迁移得到的关键规律是：路由由“事实位置 × 是否阻塞 × 判断还是生成”共同决定，不能只凭主题名称决定。
