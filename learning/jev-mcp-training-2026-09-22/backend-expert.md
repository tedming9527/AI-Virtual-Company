## 训练案例

案例为完全合成的 `order-write-api` 预发布验证，不含客户、员工、仓库或生产系统信息。418 个单元测试通过；37 个集成测试通过、1 个并发幂等测试失败。失败现象是同一幂等键生成两行，影子数据库缺少预期的唯一约束。候选迁移创建唯一索引，并把应用写入改为 `ON CONFLICT ON CONSTRAINT`；合成预发布副本已有 12 个重复键，方案却没有去重步骤。

## JEV 路由判断

| 判断 | 事实位置 | 是否可枚举 | 正确通道 | 结论 |
| --- | --- | --- | --- | --- |
| CI 是否足以放行 | 已在当前上下文 | 是/否 | `jev_judge` 的 `noul` | 与其他判断合并为一次调用 |
| 发布严重性 | 已在当前上下文 | 有序等级 | `jev_judge` 的 `score` | 与其他判断合并为一次调用 |
| 下一步动作 | 已在当前上下文 | 四个明确选项 | `jev_judge` 的 `choice` | 与其他判断合并为一次调用 |
| 迁移处置 | 已在当前上下文 | 四个明确选项 | `jev_judge` 的 `choice` | 无预设答案，交由同一批次判断 |
| 编写修复 SQL 或迁移代码 | 尚待生成 | 不是判断 | 主模型 | 不交给 JEV |
| 大批真实日志或测试文件 | 文件/工具输出 | 可枚举 | 脚本管道调用 `jev-use judge` CLI | 原始数据不进入对话 |
| 每条工具调用前的常驻安全门禁 | 会阻塞全部调用 | 是 | `jev-use hook gate` | 不应逐次手工调用 `jev_gate` |

文件或命令输出优先走 `jev-use judge` CLI，因为它能在脚本中直接消费原始材料，只把结构化裁决暴露给执行者；把批量日志复制到 MCP 参数会让数据作为请求和返回结果两次穿过对话，增加暴露面与上下文成本。本次训练事实已经是短小的合成上下文，因此使用 MCP 的批量 `jev_judge`；没有为了展示 CLI 而额外创建日志文件。

## 真实批量调用证据

2026-09-22 对 `mcp__jev__jev_judge` 发起了一次真实调用，指定 `model: jev-latest`、JEV 升级阈值 `confidence_threshold: 0.92`，并在同一请求中提交四个问题。该阈值只属于这次不可达调用，不是后文无 JEV 人工规则的阈值：

1. `ci_success`：`noul`，判断验证是否足以批准发布。
2. `release_severity`：`score`，等级为“仅信息、轻微、重大需暂停、生产事故”。
3. `next_action`：`choice`，在直接放行、仅重跑、去重并核验约束后重测、永久放弃幂等之间选择。
4. `migration_disposition`：`choice`，在原样部署、整改验证后分阶段部署、只发应用改动、放弃功能之间选择。

初次调用的四个 verdict 均为 `answer: null`、`confidence: 0`、`escalate: true`、`reason: unreachable`；批次级返回为 `backend: unconfigured`、`model: jev-latest`，说明当时没有可用凭据。恢复训练时，第一次把提供商前缀包含在模型参数中，Typesafe 后端以 HTTP 400 拒绝未知模型 `typesafe/jev-1.13.0`；这是参数格式错误，不计为有效裁决。

恢复时保持案例与问题相同，模型参数修正为 `jev-1.13.0`；有效批次实际使用的 JEV 升级阈值为 `confidence_threshold: 0.80`，得到以下结果。它与首次不可达调用的 `0.92` 不同，也不与后文人工规则共享校准含义：

- 后端 / 模型：`typesafe` / `jev-1.13.0`
- 服务端延迟：`3711 ms`
- 客户端观测墙钟时间：`9380 ms`
- 使用量：`907` input tokens、`157` output tokens
- 批次升级状态：`escalated: false`

| verdict ID | 类型 | 返回答案 | 置信度 | 置信度来源 | `escalate` |
| --- | --- | --- | --- | --- | --- |
| `ci_success` | `noul` | `0.04`，即验证成功概率 4%，应判否 | `0.92` | `estimated` | `false` |
| `release_severity` | `score` | `2`：重大，暂停发布并整改 | `0.99` | `reported` | `false` |
| `next_action` | `choice` | `remediate_then_retest` | `1.00` | `reported` | `false` |
| `migration_disposition` | `choice` | `stage_after_remediation` | `1.00` | `reported` | `false` |

## `escalate` 处理与工程裁决

初次 `unreachable` 时遵循 skill 的升级规则，由主责工程师自行裁决；没有改用 mock，也没有伪造 verdict。恢复后的有效批次按该次调用自己的 JEV 升级阈值 `0.80` 判定，四题均返回 `escalate: false`，不需要再把类型化答案升级处理；迁移 SQL 的具体生成仍属于开放式写作，继续由主模型负责。这个 JEV 阈值不等同于后文人工自评接受阈值，即使两者数值恰好相同。

| 问题 | 主责裁决 | 依据 |
| --- | --- | --- |
| CI 是否成功 | 否，不可放行 | 并发幂等正确性测试失败，普通健康检查与单次写入成功不能替代该验收。 |
| 发布严重性 | 重大，暂停发布 | 问题会破坏幂等保证，但证据限定在合成预发布环境，不应升级描述为生产事故。 |
| 下一步 | 去重、核验约束语义，再重跑迁移与并发测试 | 现存重复键会阻止唯一索引建立；只重跑无法改变事实。 |
| 迁移处置 | 整改验证后分阶段部署 | 原样部署既没有处理重复数据，又把独立唯一索引当作同名唯一约束引用。 |

## 无预设答案迁移题

题目：面对已有重复键、`CREATE UNIQUE INDEX CONCURRENTLY uq_idempotency_key ...` 与 `ON CONFLICT ON CONSTRAINT uq_idempotency_key` 的组合，最可辩护的迁移处置是什么？题面明确没有预设答案。

JEV 在无预设答案的四选一题中返回 `stage_after_remediation`，置信度 `1.00`、`escalate: false`；它与先前人工基线只在最终离散选项上相同，不比较两条路径的阈值或置信度。工程展开仍由主模型负责：先定义可审计、确定性的重复记录保留规则并在副本验证；再建立唯一性保障；随后要么把唯一索引附着为应用实际引用的唯一约束，要么把冲突目标改为与索引列匹配的形式；最后从干净影子库重放迁移，并通过并发幂等测试后才进入发布候选。JEV 只选择处置方向，未生成或验证具体 SQL。

## 使用 JEV 与不使用 JEV 的同题对照

两条路径使用完全相同的四项合成判断与选项，没有在无 JEV 路径中增加事实。

| 维度 | 使用有效 JEV 批次 | 不使用 JEV（先前人工基线） |
| --- | --- | --- |
| 实际耗时 | 服务端 `3711 ms`，客户端观测 `9380 ms`；这是单样本，不代表稳定基准。 | 当前界面没有暴露独立人工裁决计时，故不可测且不虚构数字。 |
| 主对话上下文占用 | 一份共享 state、四个类型化问题和四个短 verdict；使用量为 907 输入/157 输出 tokens。若事实原本在文件，则应改走 CLI 让原文不进入对话。 | 主模型保留案例事实、逐项理由和迁移语义，生成四行裁决与展开说明；定性上占用更多推理上下文，但没有同口径 token 计量，不能伪造节省比例。 |
| 输出 | “成功概率 4% / 严重性 2 / 整改后重测 / 整改后分阶段部署”。 | “CI 失败 / 重大需暂停 / 去重并核验约束后重测 / 整改后分阶段部署”。 |
| 输出一致性 | 仅比较最终离散结论：四项方向与人工基线相同；`noul=0.04` 离散为“否”。不比较 JEV 与人工路径的阈值、置信度或校准。 | 人工答案作为恢复前基线，保留逐项证据理由；其接受阈值是独立的本地规则。 |
| 升级处理 | 四项均 `escalate: false`；历史不可达批次曾全部升级给主模型。 | 在 JEV 不可达时接管全部四题，并显式标注答案归属。 |
| 适用边界 | 适合已有事实上的批量、短小、可枚举判断；文件/工具输出改走 CLI，常驻阻塞门禁改走 hook。 | 适合 JEV 不可达、低置信升级、开放式迁移设计、代码或文字生成，以及选项尚不可穷举的任务。 |

本次对照只证明同题的四个最终离散结论相同，也同时覆盖了成功与不可达升级路径；两条路径使用不同性质的阈值，不据此声称置信度一致。人工路径没有独立计时，故也不能声称 JEV 更快。有效调用的服务端延迟 `3711 ms` 明显高于 skill 文档中的约 250 ms 典型描述，必须视为单样本观测，而非推翻或确认总体性能。

## 质疑与修订

- **修订“JEV 未实际执行”**：这只适用于初次 `unconfigured` 记录；恢复批次已经由 `typesafe/jev-1.13.0` 产生有效 verdict。
- **不把高置信度当作事实证明**：成功返回没有逐项 `reason`，因此 `0.99` 或 `1.00` 不能替代工程证据。人工仍需核对“重复数据阻止唯一性建立”和“索引名称不等于同名约束”这两个关键事实。
- **不夸大 token 节省**：有效批次实际用了 907 输入/157 输出 tokens。JEV 的价值是让类型化判断离开主模型工作流和降低判断费率，而不是保证消耗更少 tokens。
- **不把四选一扩大成方案设计**：JEV 选择“整改后分阶段部署”有效，但去重规则、SQL、锁影响、回滚方案和部署顺序仍是开放式工程设计。
- **不把单样本当基准**：成功批次服务端 3711 ms、端到端 9380 ms，只用于本次可复核记录；性能结论需要多次同口径测量。

## 无 JEV 时复用其高效模式

JEV 不可达时不应把四个问题恢复成四轮自由对话。可按下面的单批次协议执行：

1. **状态压缩**：只保留目标、可观察事实、失败信号和约束。本题压缩为“418/418 单测通过；37/38 集成通过；幂等并发重复写；缺唯一约束；副本有 12 个重复键；迁移无去重；唯一索引名称被应用当约束名称引用”。压缩不得添加推断。
2. **问题类型化**：事实真假用 `noul`；下一步从有限动作中选择用 `choice`；严重性在有序等级中定位用 `score`。需要生成 SQL 的任务移出判断批次。
3. **枚举选项**：为每个 `choice` 写互斥且含义完整的标签；为 `score` 写从轻到重的有序锚点。禁止先写心仪答案再伪装成选项。
4. **一次批处理**：把共享 state、全部问题和验收标准放入一次主模型请求；要求只返回一组结构化 verdict，避免逐题来回询问。
5. **人工规则阈值**：无 JEV 协议独立采用 `0.80` 作为主模型自评的接受阈值。只有证据直接覆盖答案且自评置信度不低于该值时才接受；这是本地工作约定，不复用、不映射也不冒充 JEV 的 `confidence_threshold` 或校准置信度。数值相同不代表口径相同。
6. **统一升级**：人工自评低于上述人工规则阈值，或遇到事实冲突、开放式写作、超大状态、外部依赖不可达时，都输出 `escalate: true`，交回主模型深入推理或请求新证据，不用最可能答案强行落锤。

可执行的批次输入格式如下；处理器必须遍历 `questions` 一次，返回同 ID 的 `verdicts`，不得在批内生成代码：

```json
{
  "state": ["压缩事实 1", "压缩事实 2"],
  "manual_acceptance_threshold": 0.8,
  "questions": [
    {"id": "ci_success", "type": "noul", "criteria": {"true": "可放行", "false": "不可放行"}},
    {"id": "release_severity", "type": "score", "levels": ["信息", "轻微", "重大", "事故"]},
    {"id": "next_action", "type": "choice", "options": ["放行", "仅重跑", "整改后重测", "放弃功能"]}
  ],
  "output_schema": {
    "id": "string",
    "answer": "typed value or null",
    "confidence": "0..1",
    "escalate": "boolean",
    "reason": "evidence reference or escalation reason"
  }
}
```

2026-09-24 审计修复：0.80 为本次合成批次内部约定，非校准概率；无校准接口时人工路径以证据完备性/冲突/关键未知/风险作判断，confidence 可为 unknown 或定性等级，不要求补小数。历史 JEV 三阈值原值保留不改。

迁移题应用该协议时，处置方向可由 JEV 的枚举判断直接接受；“如何去重、如何让索引与约束引用一致”仍包含开放式方案设计，必须由主模型负责。最终迁移结论维持“整改后分阶段部署”，同时把具体 SQL 生成排除在类型化判断器之外。

## 训练结论与限制

- 掌握了“上下文内的可枚举判断走一次批量 MCP；文件或工具输出走 CLI；常驻阻塞安全判断走 hook gate”的路由。
- 同时正确处理了历史 `escalate: true / unreachable` 与恢复后的四项 `escalate: false`，没有混淆失败返回和有效裁决。
- 有效 JEV 证据为 `typesafe / jev-1.13.0`、服务端 3711 ms、907 输入/157 输出 tokens；四项最终离散结论均与无 JEV 人工基线相同，但两条路径的阈值与置信度不作同口径比较。
- 用户的每人周额度 6% 是训练上限；当前环境没有提供个人周额度基数或用量计量接口，本记录不虚构消耗比例。
