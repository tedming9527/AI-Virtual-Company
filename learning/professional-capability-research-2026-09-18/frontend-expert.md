## 共同主题理解

“一次做对”不是追求零修改，而是让第一次方案建立在正确的页面职责、真实设计实例、完整状态空间和相称证据上。AI 的价值应是更快完成定向检索、状态枚举和验证编排；专业判断负责拒绝错误抽象、证据越级与无意义重试；跨岗位协作只有形成可定位的设计交接或质量结论才算发生。这样减少的是可避免返工，不是正常迭代。

## 近期核心问题

1. 独立页迁移容易从“复制旧弹窗并补 CSS”起步，页面壳、导航、数据状态和内容区职责随后反复搬动。
2. Figma 截图、节点属性、图片像素推断和代码默认值常被混为一层；顾问名字也可能先于真实交接出现。
3. 首屏正常态容易掩盖 loading、empty、error、直达、返回刷新及乱序响应；构建或 jsdom 通过又容易被写成浏览器与真实接口已验收。

## 专项结论与证据

页面正确性应按“路由页壳 → 纯内容区 → 状态/请求契约 → 分层验证”组织，而不是按视觉块机械拆文件。

## 三条行动规则

1. **先立证据账本再写样式。** 对每个关键尺寸或状态标记来源：Figma 节点、截图推断、代码事实、浏览器观察或接口回执；无来源即 unknown，不用“看起来像”补成事实。
2. **先分职责再拆组件。** 路由页拥有页面壳、导航、加载/错误/空/内容与返回策略；内容组件只处理搜索、列表和选择；请求层保留结构化错误及请求归属。只有独立变化原因才新增抽象。
3. **先定义全状态再宣布通过。** 用 Debug 浮板探索视觉组合、纯逻辑测试锁定映射/权限/请求归属、路由或端到端测试守关键旅程；构建、Mock、浏览器、真实接口结论分别报告。

## 成功案例与反例

项目选择页只能作为历史任务记录所述的有限正向样本（记录层样本）：该记录尝试把独立页职责、选择返回、设计节点与验证项放入同一交付叙述，方向上符合证据账本思路。由于记录自身存在执行者与状态冲突，且本轮没有代码、实际执行者、测试原始回执、浏览器或接口证据，它只能证明记录层信息可追溯，不能证明真实页面已实施成功，也不能证明所述行为或设计还原已经通过。

反例来自 `flexible`：旧请求被 abort 后被转换成空列表成功。其视觉结果可能“干净”，但语义把取消伪装成 empty；若再让旧请求改写 loading/error，页面会同时失去数据真值与错误真值。结论是 AbortController 只能节省或中止传输，正确性仍需请求所有权与明确取消状态。

## 未预给答案的迁移题与独立作答

**题目：** 把订单页的“切换社区”抽屉迁成独立路由。设计稿只给正常态和空态；用户从社区 A 进入，搜索并选择 B，返回后 A 的慢请求最后到达；页面也允许直接深链进入。如何架构和放行？

**作答：** 路由页承载导航、当前社区、直达初始化及 loading/empty/error/content/selecting 六态；列表内容不拥有返回与刷新。进入和每次搜索生成 `requestStamp`，A 的 rows/loading/error 回写均因归属不匹配被丢弃；选择 B 后以规范 URL replace 返回，主页面按 B 新建请求归属。设计稿未给 error/selecting 时只复用已审系统组件并登记设计 unknown，不臆造节点数值。放行至少需要：deferred Promise 乱序单测、路由直达/返回测试、目标视口浏览器检查；真实接口未通则结论为 partial。该答案只证明案例迁移推理，尚未在生产代码复现。

## 可复用检查清单

- 目标路由、layout、现有组件、状态/请求层是否已定向定位？
- 节点 ID、实例尺寸、截图与推断是否分栏记录？
- loading/empty/error/content/选择中/直达/返回是否有归属者？
- data、loading、error 是否由同一请求身份保护？
- Debug fixture 是否与单测共源、默认关闭且禁用真实副作用？
- 代码、浏览器、接口与设计证据是否各自只支撑同层结论？
- 涉及 Figma 时使用 `figma-reader` 读取真实节点；涉及 React 样式时使用 `react-scoped-styles`，但 Skill 不替代项目事实。

## Unknown、下一次应用与返工指标

Unknown：历史节点当前是否漂移；项目选择页真实浏览器表现、接口失败态、可访问性及设计师实际交接；该流程是否降低长期返工。

下一次同类真实任务先提交一页“职责图 + 状态矩阵 + 证据账本”，完成正常态、失败态与选择返回的一条纵向链路后再扩展；首次报验必须包含真实视口和接口层结论，缺一项就明确 partial。

主指标为 `rework_rounds`：仅统计因不满足已约定布局、状态或行为而被用户退回的轮次，新增需求另记 `scope_changes`。辅助记录首次报验已验收状态数/必需状态总数。后续三个可比 UI 任务只校准基线，不提前承诺下降比例或因果提效。
