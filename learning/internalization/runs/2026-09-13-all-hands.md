## 参与与资源边界

- Primary：陈知行 · 路由官；consult：辛澈 · AI工程师。
- 实际执行：`root` 负责业务相关者与整合；三个异步 sub-agent 分别承担经验提取、反例质疑和迁移建模，之后一个分身在不查看运行文件/rubric 的条件下作答新题。
- 逻辑身份：三个分身在每个段落都切换为同一名员工，不把三个分身伪装成三名员工。
- 用户本轮专项目标：每岗 10% Spark、聚合目标 80%。实际分身使用了继承模型而非显式 Spark；运行后 Spark 五小时与周窗口均为 0%。该错误不再以 `unknown` 掩盖。
- 并发：环境最多四个活跃智能体，保留主责协调槽，三个工作槽异步并行；共享文件由主责串行写入。

## 未见迁移题结果

1. 路由：面对“跨五目录文案”和“单行生产权限”同时到达，作答分身没有按规模统一定级，而是拆成 S 与 L；环境事实未核实时停止权限项。
2. 产品：面对留存上涨但高风险误操作翻倍且人群改变，拒绝推广，先处理护栏和混杂。
3. 前端：面对两次退款乱序与超时后远端成功，按业务单号分别展示，超时进入结果查询，不自动当失败重试。
4. 后端：面对下游不幂等但可查询，使用稳定指纹先查询，同时承认“查询—执行”非原子时不能保证零重复。
5. 设计：面对 30 秒延迟发送，仅在窗口内提供取消；发出后明确不可撤回并提供真实补救路径。
6. 测试：拒绝把 JSON 结构绿色和三分身一致意见写成“已经举一反三”。
7. AI 工程：把三篇互引文章识别为循环引用，只写官方已确认收报；修复状态和版本保持 unknown。
8. 培训：拒绝把预估佣金、平台结算和已收款相加，以业务状态与事实归属验收学员，而非只看 BigDecimal 测试。

这些答案均改变了至少两个场景轴，并指出不变量、unknown 或停止条件；具体题目、第一答案、质疑与修订保存在 JSON。产品与 AI 工程在题设事实内通过 `reviewed_case`；其余六岗因交叉质询暴露了必须回业务事实源的缺口而保持 `held`。没有一岗升级为 `verified_context`。

## 技术架构

核心管线为：

```text
岗位事实源快照
  → 经验提取分身
  → 反例质疑分身
  → 冻结知识草稿
  → 迁移建模分身出新题
  → 未见答案分身作答
  → 业务相关岗位交叉质询
  → 主责整合为 candidate
  → 按知识维护门禁决定是否发布
```

机器记录采用：

`Trigger → Signals → Decision → Action → Evidence → Limits → Counterexample → Transfer test`

每个来源保存公司根目录相对路径与 SHA-256；校验器会核对花名册八岗覆盖、三分身角色、业务对话、两条以上变化轴、证据级别、来源哈希和本轮 10% 上限声明。哈希只证明读取源未漂移，不证明语义正确。
