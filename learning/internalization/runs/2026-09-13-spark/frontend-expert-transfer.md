## 一、异步对话重建

### 业务相关者质疑
1. 设计侧质询：在“AI 自动执行/延迟发送”高风险动作中，若未确认后端不可撤回能力，是否能上线“取消”按钮？是否能在前端承诺“系统会自动补救”？  
2. 后端侧质询：前端“取消请求”或加载态切换是否能保证远端副作用不重复？  
3. 测试侧质询：当并发与超时场景仍有 `unknown`，但视觉验收与主流程截图达标时，是否允许灰度上线？谁负责什么时候触发人工对账？

### 本岗回应（第一轮）
1. `frontend-expert-extract` 的第一条经验要求所有异步回包必须带上下文归属（如关键词快照/请求序号），并在归属不匹配时丢弃旧响应，避免“新筛选下被旧数据覆盖”。该规则可直接用于高风险 AI 操作页面，先保证视图真值不被过期回包污染。  
2. `frontend-expert-extract` 与 `backend-expert-extract` 都不支持“前端取消即等同后端幂等成功”；因此不能以前端交互动作替代服务端副作用边界。  
3. 结合 `design-master-extract`，高风险动作必须在执行前明确流程阶段，并禁止在未确认真实业务契约时承诺“可撤回/自动补救”；执行后应展示可追踪终态。  
4. 结合 `test-expert-extract`，构建绿灯、静态通过或截图合格只能作为分层证据，不能直接触发 release，尤其不能掩盖并发/超时 `unknown`。  

据此初步决策：  
- 保留“请求归属优先于 UI 禁用状态”的一致性原则；  
- 将“可撤回/补救承诺”默认移到后端契约验证后再声明；  
- 在并发/超时未知未闭环前，默认不把高风险路径列入灰度放行队列。  

### 反质疑（第二轮）
- 反质疑点 A（后端）：“如果用户频繁改条件，快速响应体验会否退化？”  
  回应：通过保持请求归属 + 只更新当前生效版本，可以既保障体验速度（保留加载/结果更新），又防止旧回包污染；并发下不改变用户时延上限。  
- 反质疑点 B（测试）：“如果高风险动作阻塞太久，节奏会拖慢发布？”  
  回应：引入分层发布门禁可避免“看起来可用、实际不可追责”。对于高风险动作，发布优先级由可恢复性与终态可追踪性决定，不是看视觉修复速度。  
- 反质疑点 C（设计）：“是否可以先给‘可取消’按钮当过渡提示？”  
  回应：可给“处理进度/联系方式”过渡说明，但不得使用“可撤回/自动补救”文案，除非后端返回可执行且可验的能力证明。  

### 修订决定
1. **保留规则（不变）**：所有有“搜索/筛选/并发提交”属性的异步交互，必须实行“请求归属快照 + 归属匹配才更新视图”。  
2. **修改规则（新版本）**：在高风险 AI/交易类动作发布页，所有按钮与状态文案进入二级决策：  
   - 当后端返回 `cancel_supported=false` 或未返回 `execution_contract` 时，前端禁止展示“可撤销/自动补救”承诺；改展示：  
     - `提交后以服务端执行回执为准`  
     - `请使用任务状态页查看最终执行结果`  
     - `失败可人工介入`  
   - 当且仅当服务端返回可验证的 `cancelSupported` 与 `finalizationWindow` 时，允许展示“可取消/补救”按钮，并绑定后端实际生效窗口。  
3. **修改规则（放行）**：并发/超时场景若有 `unknown`，无论主流程截图是否达标，均不能列为灰度候选；需先形成“失败明细 + 人工对账时限 + 责任人”。  

## 二、跨场景迁移题（未预先给答案）

### 题目
一张“会员续费提醒”页面新增“AI 代发提醒”功能：用户可在同一页面完成关键词筛选、编辑后置参数并点击“提交”，系统会在 5 秒内异步排队后向外部渠道发送消息。  
条件变化：  
- 输入来源变更：从本地列表改为“跨组织模板库 + 个人草稿库”双源。  
- 风险提高：每条任务有“是否可取消”的后端字段，有时返回空。  
- 任务窗口变短：从原先的 60 秒结果回填改为每 5 秒轮询 `task-state`。  
要求：给出前端策略，并定义何时能进入灰度。  

### 本岗作答
- 采用“请求归属 + 双轨状态面板”：
  - 每次提交创建 `request_stamp`（包含筛选快照、组织 ID、模板来源、目标用户数）；每次回包和轮询结果先校验 `request_stamp`。
  - UI 只在当前有效 `request_stamp` 下展示“处理中/成功/失败/部分成功/执行中待确认”四态，不允许只显示单一成功图标。  
- 高风险动作按 `cancelSupported` 分支：
  - `false/unknown`：禁用“撤销承诺”文案，显示“提交后以执行结果为准”；保留客服/工单入口。  
  - `true`：展示撤销窗口与窗口倒计时；倒计时结束后自动降级为后者文案。  
- 三层验收覆盖：
  - 体验层：状态一致性（无旧响应污染）、可视状态完整性（含错误/超时/部分成功）。  
  - 逻辑层：接口参数快照一致性、轮询终态一致性。  
  - 可靠性层：并发提交与超时分支需有失败明细（任务粒度）和恢复路径。  

### 修订后的决策结果
- 在该题下，若用户快速改条件导致 2 次以上重试，旧响应将被抛弃，不可刷新旧状态。  
- 若任一任务批次出现部分失败且缺失明细，不得进入灰度。  
- 仅当所有高风险路径可见终态闭环，且 `unknown=0` 时方可灰度。  

## 三、验收规则（迁移题）

### PASS 条件
- 1）请求归属校验  
  - 规则：同一页面 1 分钟内至少 3 次快速连续触发重试时，最终只保留最后一次请求的终态更新。  
  - 验收方法：手工重放与接口抓包核对。
- 2）高风险动作文案边界  
  - 规则：后端未返回可验证可取消能力时，页面不得出现“可撤回/自动补救”承诺文案。  
  - 验收方法：静态文本与交互状态覆盖检查（含多语言/暗色/窄屏）。
- 3）并发未知阻断  
  - 规则：并发/超时场景存在 `unknown` 时，灰度状态为 `blocked`，并自动附带人工对账触发项（owner + 处理时限）。  
  - 验收方法：测试用例与发布清单双签。  
- 4）失败可观测性  
  - 规则：每个任务批次必须输出至少 3 类终态统计（Success/RetryableFailure/Failed）及任务 ID 对应明细。  
  - 验收方法：日志与状态页一致性审计。  

### 留档与边界
- 该迁移题只用于架构迁移训练，不作为生产发布结论；真实上线需按 DELIVERY_POLICY 与对应项目验证链路补验。  

## 四、可复用架构单元与边界

### 可复用单元 A：`request_affinity_guard`（请求归属守卫）
**职责**：防止过期异步回包污染最新视图；保持列表/状态与当前筛选一致。  
**边界**：不承担服务端幂等与重试副作用；只保证前端可见状态单点真实。  

### 可复用单元 B：`high_risk_action_gate`（高风险动作门禁）
**职责**：根据后端契约动态切换是否展示撤销、是否允许补救承诺、是否进入灰度。  
**边界**：不决定服务端可撤销时长和补偿规则；只在 UI 层暴露和提示已验证能力。  

### 可复用单元 C：`stateful_acceptance_matrix`（多层验收矩阵）
**职责**：把三类验收（体验、逻辑、可靠性）强制串联，避免“截图通过”误放行。  
**边界**：不替代独立评测；仅定义交付门槛与证据项。
