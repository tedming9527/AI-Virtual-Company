## 经验 1：租约恢复与跨系统副作用不能只靠本地回写防重放

**触发信号**
- W1 挂起、租约到期后被 W2 重领、W1 恢复继续执行
- 远端接口在本地回写失败后仍可能已真实落库

**状态/责任边界**
- 本地 `owner/token` 回写只负责该次本地状态的所有权与并发覆盖边界，不能覆盖远端副作用；
- 跨系统幂等与回滚责任在外部服务契约（是否支持去重/查询）；
- `unknown` 结果（超时/响应丢失）是独立状态，不可直接转成“失败可重试”。

**决策规则**
在租约恢复场景把“领取所有权、本地回写、远端副作用”三类事实分离；对同一业务操作必须复用稳定业务键，不要把重试追踪 ID 当作去重键；若下游无幂等契约则走有界恢复与对账/人工处置。

**证据**
- `employees/backend-expert/KNOWLEDGE.md`：岗位条目“跨系统副作用与幂等边界”明确三段分离与 `owner/token` 边界。
- `learning/2026-09-11-remaining-roles-retraining.md`：W1 本地回写被拒绝但远端可能已扣款的反例修订结论。
- `learning/evaluations/2026-09-11-workflow-v1/backend-cold-final.md`：同类评审中明确“本地回写不能阻止远端重复副作用”。

**反例/失效条件**
- W1 挂起后恢复，尽管它的本地 `owner/token` 回写被 `0 行` 拒绝，W1/W2 都可把同一业务动作发送到下游，导致重复扣款或重复导出。

## 经验 2：超时后不得更换去重键，必须保留业务键并区分尝试标识

**触发信号**
- 执行超时或响应丢失后进入重试分支
- 重试链路出现相同业务操作、不同尝试记录时

**状态/责任边界**
- 业务级“操作ID/指纹”应长期一致，并用于外部幂等对账；
- `trace/request id` 可变，用于链路可观测性，但不能承担外部去重职责；
- 未知结果由恢复状态控制重试边界（次数/窗口），不应无限重试。

**决策规则**
超时只代表“结果未知”，不代表“未执行”；重试使用新追踪 ID 也要复用同一业务键。若下游不支持幂等或查询，必须在达上限后中止自动副作用重试并转人工核对。

**证据**
- `learning/evaluations/2026-09-11-workflow-v1/backend.md`：明确拒绝“换幂等请求 ID”并要求稳定业务键。
- `learning/evaluations/2026-09-11-workflow-v1/backend-cold-final.md`：将“超时不可直接判定失败/未执行”列为核心证据，并提出按原业务键恢复与对账。
- `employees/backend-expert/KNOWLEDGE.md`：将稳定业务键与对方去重/查询契约作为复用条件。

**反例/失效条件**
- 在超时后把下游去重键替换，可能把本次重试当新业务操作，产生重复计费、重复推送、重复导出等副作用。

## 经验 3：远端回调/推送缺少 outbox 时存在“提交后/落库前”缺口

**触发信号**
- 本地事务提交后依赖 `afterCommit` 调外部系统
- 外部调用成功但落库状态未落盘，或服务进程崩溃

**状态/责任边界**
- `afterCommit` 只是调用时机，不等于可靠消息；外部副作用与状态记录都可能在崩溃窗口丢失；
- 重试任务若无原子 `claim/lease` 与唯一约束，易产生重复扫描或并发冲突。

**决策规则**
在本地事务内持久化 outbox（或同等原子记录），执行器按 `Pending → Processing(owner, leaseUntil) → Success/RetryWaiting/Dead` 抢占；下游调用用 `sourceId` 去重，并保留重试上限与告警。

**证据**
- `learning/2026-09-13-vanke-backend-project-distillation.md`：Camille 小节列出 `afterCommit` 之后的丢失窗口、重试缺口、建议改造（outbox + 状态机 + lease）。
- `learning/2026-09-13-vanke-backend-project-distillation.md`：Mephisto/BlackSam 等案例对“先查询再写/全局锁”单点方案给出“只能部分借鉴”结论，说明缺乏完整可靠性边界。

**反例/失效条件**
- 仅用全局锁且无租约/claim 时，锁超时后可能并发重复执行；`afterCommit` 与记录落盘之间崩溃导致外部推送永久丢失。

## 经验 4：批处理“部分成功”必须显式状态化，不可直接当成功返回

**触发信号**
- 循环内单条处理失败可被吞掉继续提交
- 任务返回值与下游失败清单不一致

**状态/责任边界**
- 成功判定必须体现“哪些对象成功、哪些对象失败、如何重试/补偿”的明细；
- 产线指标中的 `result.size()` 不可替代完整任务正确性。

**决策规则**
把每条子任务映射到 `Pending/Processing/Success/RetryWaiting/Failed` 或同等状态机；不允许静默吞错后仍对外宣告全量成功；失败明细与重试入口是恢复前提。

**证据**
- `learning/2026-09-13-vanke-backend-project-distillation.md`：BlackSam 汇总流程单工人失败仍 `handleSuccess` 的反例与待验证问题。
- `learning/2026-09-13-vanke-backend-project-distillation.md`：Camille/订单重试链路强调逐条隔离和状态化；仅日志/字段不足以证明补偿闭环。

**反例/失效条件**
- 任务内 1 个工人/订单失败被记日志后，其余条目继续返回，业务收到“完成”但缺失重试清单，后续对账和核销无法收敛。
