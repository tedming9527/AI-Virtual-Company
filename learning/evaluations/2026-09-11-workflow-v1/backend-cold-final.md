## 风险与设计决定

1. **本地回写条件无法阻止远端副作用。** 可出现 W1 挂起 → 租约过期 → W2 原子接管 → W2 调用远端成功 → W1 恢复也调用远端成功 → DB 拒绝 W1 的旧 owner 回写。最终本地记录可能正确，远端却执行两次。领取、回写、远端资源必须分别证明其并发控制。调用前检查 owner 仍有“检查后挂起、接管后恢复”的窗口；续租、取消或租约到期本身也不保证旧进程停止。
2. **区分业务幂等键和每次尝试的追踪 ID。** 同一业务操作首次发送前持久化稳定幂等键，W1、W2、超时重试均复用它；请求追踪 ID 可以每次不同，但不能替换远端用于去重的业务键。fixture 未说明请求 ID 是否承担幂等职责，因此“换 ID 必然重复”也不能直接断言；若它是去重键，换新 ID 将使对方可能当作新业务操作。新业务操作应获得独立键，不能让不同操作被错误合并。
3. **必须核实远端契约。** 确认幂等键作用域、同键并发时的原子去重、相同键不同负载的拒绝规则、去重与实际副作用的一致性、结果重放或查询能力、有效期及恢复最长窗口。仅客户端传键不足以证明远端去重。未核验这些能力前，不承诺恰好一次。
4. **fencing 仅在受保护资源校验时成立。** 若使用单调递增 token，下游必须在执行副作用时原子拒绝旧 token，并持久化正确的最大版本。仅本地 DB 校验或在请求中携带 token 均无效。fencing 也不能替代同一业务操作的幂等处理：较旧请求可能在下游见到新 token 前已执行，之后新执行者仍需识别该业务操作已完成。
5. **超时是结果未知，不等于确定失败。** 为未知结果保留原业务键、尝试与查询记录；优先按原键查询或按契约安全重试，设置次数、退避、期限及停止条件。远端成功、本地回写失败时通过结果查询与对账补齐本地状态，不能把所有异常立即转回可重复执行状态。远端无可靠去重且无法确认结果时，停止自动副作用重试，交由对账或人工决策；不能用无限重试制造确定性。补偿本身也需独立授权与幂等设计，本次不执行。
