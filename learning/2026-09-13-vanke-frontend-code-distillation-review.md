## 一、总判断

主报告已经回应用户“不是什么都学”的要求：只提炼 4 条候选规则，逐项目区分“优点 / 缺点 / 可学 / 不学”，并明确旧栈、吞错、前端权限替代后端授权、跨业务复制财务公式等拒绝项。这一方向可保留。

主要质量问题不在定性取舍，而在量化表达：四项评分只有名称，没有可复算的分档锚点和逐项证据，因此 `83/100`、`71/100` 等数字呈现了超过现有证据的精度；其中 18 个非深读仓库尤其不足以支持逐分排序。`azeroth` 可以保留为“本轮静态研读首选”，但不能由当前证据推出“总体工程质量第一”或“唯一具备这些能力”。

## 二、必须修订项

当前四项各 25 分只定义了关注内容，没有定义 0、5、10、15、20、25 分分别需要什么证据，也没有记录每个仓库每项扣分原因。相同事实无法由另一位评审稳定复算出 `23/21/17/22`。

2. 保留百分制，但增加固定锚点、每项事实引用、静态证据置信度，并让全部 23 个仓库接受同等深度的抽样。

在完成前，`83/100` 只能标为“当前评审者的启发式静态分”，不能叫严格评分。

### M2：收窄 `azeroth` 的“83 分且首选”结论

可保留的结论是：**在本轮已深读样本中，若目标是学习请求边界、权限声明和行为测试，`azeroth/karazhan` 是首选入口。**

必须删改两处过度推断：

- “唯一同时具备……”需要对其余 22 个仓库逐一按同一检查表排除；主报告又明确未逐一深读，因此应改为“本轮检出的最完整样本”。

`azeroth` 的工程成熟度给到 21/25 也需要重新解释：三个子项目确有完整 `check` 脚本和大量测试文件，但当前工作流只调用 `npm ci` 与模块 `build`，且本轮没有执行任何脚本、没有读取 CI 历史。若保留 21 分，必须说明“脚本存在”和“门禁执行”各占几分；否则建议取消精确分数。

### M3：修正 `azeroth` 文件/测试数量的口径混用

主报告写“约 223 个 JS/TS/TSX 文件中发现 77 个测试文件”。复算结果：

- `*.{js,jsx,ts,tsx}`：223 个；同扩展名的 `*.test.*`/`*.spec.*`：68 个。
- 若把 9 个 `*.test.mjs` 纳入测试数，则源码扩展名也应同步纳入 mjs/cjs：总数 232、测试数 77。

必须选择同一扩展名集合，并在报告中给出命令口径。还应把“测试密集”拆成两层：77 是命名匹配数量，其中至少 18 个文件名带 contract/migration/style/deployment/build/route 等静态契约特征，29 个是 `*.test.tsx`；文件名数量不能直接等同于用户行为覆盖或测试已通过。

`katarina` 的 4,505 个 JS/TS/Vue 文件和同一命名规则下 0 个测试文件可以保留，但须继续写成“当前快照按该命名模式未检出”，不能写成绝对不存在任何测试或生产质量差。

### M4：把 CI 配置事实与 CI 运行结论分开

可确认的静态事实：当前唯一检出的 `.github/workflows/cicd.yml` 在前端步骤执行 `npm ci` 和 `npm run build:<module>`；三个前端 Dockerfile也只执行安装与 build；未检出 `check/test/lint/typecheck` 调用。

因此报告应统一改成：**“当前已检出的入库 CI/Docker 配置没有调用前端 `check`。”** 不应写成“CI 从未执行检查”或据此推断分支保护、历史流水线结果、线上质量。当前报告末尾已把 CI 历史列为未验证项，这一边界应前置到首次提及处。

### M5：收窄没有直接证据的效果性表述

以下句子应改成代码层面的可验证效果：

### M6：把“我们水平更高”落成验收门槛，而不是未经证明的排名

## 三、可保留项与证据边界

### `azeroth`

- 可注入 fetcher、动态 token getter、结构化错误 `status/code/traceId`：由 `karazhan/src/services/request.ts` 直接支持。
- 请求行为测试覆盖动态 token、匿名请求、后端结构化错误、非法 JSON：由 `request.test.ts` 直接支持，但本轮未运行，措辞应为“测试代码覆盖”，不是“测试通过”。
- 权限词汇、角色映射和路由 `access` 声明分离：由 `permissions.ts` 和 `config/routes.ts` 支持。
- `OrderListPage` 保存 URL 查询、分页保留筛选、失败保留旧数据：实现与测试代码均可支持；`active` 只阻止旧 effect 写状态，不取消网络，也不提供跨请求 ID。
- README 明确当前重文档/规格、dalaran 页面使用本地示例数据：可支持“运行联调与交付成熟度未知”。

### `flexible`

- 请求 host/token/abort 的中间件拆分、工单列表新请求 abort 旧请求：代码直接支持。
- 取消在 `TakeTaskService.fetchList()` 中被转换为 `{data: [], total: 0}`：可支持“不应把取消伪装为空数据成功”的反例。
- `ListPresenter.loadMore()` 在 `finally` 中请求 count：无论列表成功失败都会触发，结论成立。
- 收入历史核验 worker mobile，`baseCommission + adjustAmount` 集中转换并保留 null：当前分支代码支持；财务公式只限该已核对链路，不能迁移到其他系统。
- 收入历史组件具备 loading/error/empty/retry 与 effect cleanup；按当前命名规则未检出收入相关测试，边界清楚。

### `amumu`

- 路由模块化、Pinia 跨模块状态边界、多容器适配：可作为代码组织样本。
- Axios 响应错误处理在 401 分支直接 `return`，调用者会得到已解决的 `undefined`；这是明确缺陷。
- `getOrgTree()` 在 await 失败时无法复位 loading；随机 5 位构建名破坏稳定内容哈希；模板重复调用过滤函数：均由代码直接支持。
- “组织树分层更易维护/定位”属于合理设计推断，不应写成已经测得的效率收益。

### `katarina`

- URL 字符串特判多协议、默认 timeout 被每次请求赋值覆盖、interceptor 错误回调不返回 rejection、非 loading 请求失败也调用 `endLoading()`：代码直接支持。
- 表格 service 使用 `try/finally` 收口 loading；递归建树每层 filter 全量数据且根编码按环境硬编码：代码直接支持。
- 前端菜单/路由校验不能证明后端授权，保留该安全边界。

### `pretty-home`

- 小程序分包、`old-pages`、多登录/定位约束：可作为存量迁移样本。
- Promise 链末尾 catch 引用了其词法作用域外的 `reject`，会掩盖原始异常；失败业务码仍可能 resolve：代码直接支持。
- Redux logger 无环境分支地加入 middleware：可说“生产构建路径也会包含 logger，存在状态暴露和开销风险”；未打包运行，不能声称已实际泄露。

## 五、未提前给答案的最小迁移题

候选规则：**异步状态按请求所有权验证。**

### 题目

为一个搜索列表实现最小控制器 `SearchController`。它只暴露：

```ts
type ViewState = {
  keyword: string;
  rows: string[];
  loading: boolean;
  error: string | null;
};

interface SearchController {
  getState(): ViewState;
  search(keyword: string): Promise<void>;
  retry(): Promise<void>;
}
```

API 由题目环境注入：`fetchRows(keyword): Promise<string[]>`。不得修改 API 签名，不依赖真实网络，不要求使用特定框架或特定取消技术。

测试会制造以下时序，候选人事先看不到测试实现：

1. 发起 `search("旧")`，尚未完成时发起 `search("新")`。
2. “新”先成功返回 `["N"]`。
3. “旧”随后失败，错误为 `old failed`。
4. 用户点击 `retry()`，重试请求返回 `["N2"]`。

### 验收条件

- 第 2 步后页面状态为 keyword=`新`、rows=`["N"]`、loading=false、error=null。
- 第 3 步不能覆盖第 2 步的 rows、loading 或 error。
- `retry()` 必须重试“新”，最终 rows=`["N2"]`。
- 任一 Promise 都必须正常收口，不产生未处理 rejection。
- 提交内容只包含实现与最小测试；测试必须用可控 deferred Promise 主动构造上述乱序，不能用定时等待碰运气。

### 评审关注点

只按外部行为判定，不因使用某个熟悉 API 自动通过。通过本题只能证明候选人能在最小案例中处理请求所有权与乱序失败，不能证明生产项目中的复杂联动、网络取消或框架生命周期已经可靠。

### 迁移题独立验收

独立执行：

```text
node --test search-controller.test.js
tests 1; pass 1; fail 0; exit code 0

node --check search-controller.js
node --check search-controller.test.js
两项 exit code 0
```

行为复核：

- 测试通过 `deferred()` 暴露每个请求的 resolve/reject，明确控制“旧请求未完成 → 新请求发起 → 新请求成功 → 旧请求失败”的顺序，不依赖定时等待。
- 每次 `search()` 递增 request ID；成功与失败分支都只允许最新 ID 写 `rows/loading/error`。新请求成功后状态为 `keyword="新"`、`rows=["N"]`、`loading=false`、`error=null`；旧失败随后被忽略，未污染当前 error、loading 或 rows。
- `retry()` 读取当前 state 的 keyword。测试直接断言第三次请求关键词为“新”，随后验证 `rows=["N2"]`。
- `oldSearch`、`newSearch` 和 `retry` 三个 Promise 都被 await；实现捕获请求 rejection，独立测试进程没有未处理 rejection，所有 Promise 正常收口。

### 剩余边界
