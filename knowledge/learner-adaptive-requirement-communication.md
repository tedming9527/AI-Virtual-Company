# 面向跨领域读者的需求说明与理解门槛

- ID：`learner-adaptive-requirement-communication`
- Owner：沈砚舟 · 后端培训导师（资深后端架构师）
- Contributors：林知夏 · 目标规划官（Product Manager）、周启明 · 体验工程官（Frontend Engineer）、陆行远 · 可靠服务官（Backend Engineer）
- 状态：`candidate`
- 日期：2026-09-22
- 置信度：medium（单个真实案例复盘与跨岗位审查；尚无三个可比任务的效果数据）

## 触发与问题

满足任一条件时采用：

- 读者有工程经验，但对当前业务域、系统边界或目标技术栈陌生；
- Issue 先列接口、字段、路由、权限或兼容规则，读者不能复述业务目标与主流程；
- 代码已经实现，用户仍不能解释核心实体、状态、数据权威或失败结果；
- 同一流程连续出现两次局部纠正，或一次纠正会改变角色、入口、主旅程、新旧分流、数据来源或写请求责任。

本条不把“技术年限”和“领域熟悉度”混为一谈。对资深前端、采购领域陌生且正在学习后端的读者，应省略基础编程教学，先补足当前任务必要的领域语义、数据权威与状态；幂等、失败与恢复按风险展开。

## 案例证据与根因

WO 维修领料 H5/PC 需求曾直接使用如下表述：

> 缓存响应中的 businessScene、数值型 repairContextVersion、cityCode、companyOrgCode、orderBelongOrgCode；
>
> materialDetailList=[] 按正常结果处理；
>
> companyOrgCode 只用于材料可见范围，不能作为最终采购公司。

另有“先向 Meteorite 获取当前领料上下文”的描述。上述内容可能是必要契约，但它们没有先说明：谁在什么场景领料、H5/PC/Meteorite 分别承担什么、为什么需要上下文、哪些业务对象被筛选、哪个系统对最终采购公司有解释权、空列表在用户旅程中意味着什么。因此读者被迫从字段反推业务。代码完成只能证明实现状态，不能证明需求已理解、接口已联调、功能已上线或生产效果成立。

根因不是“用户能力不足”，而是需求说明没有同时建立业务叙事、领域模型和实现映射；说明者还错误地把读者的通用工程经验等同于其对陌生业务域和后端可靠性机制的熟悉程度。

## 首次最小说明与团队内部核对

面向用户首次呈现：目标、3—7 步主线、关键对象/状态、一个当前重要失败和关键未知，以一页作为信息入口，不是压缩硬门槛。必要语义超出一页时分步展开，不能为了版面限制压缩或隐藏必要的角色、状态、数据权威、失败结果与 `unknown`。先做不计失败的短诊断，再补必要领域事实/完整最小例，请用户解释，最后安排延迟独立检索。未提供业务事实归需求缺口，不要求用户猜测，也不据此重讲熟悉的编程基础。

以下六层是团队内部核对框架，不是每次必须向用户展示的六段教材。先判本任务适用性并保留简短理由，已有共同上下文链接复用；面向用户只随当前问题与风险逐层展开，不重复三岗位清单。内部核对不要求用户逐项批准，也不能替代必要运行验证。

## 内部分层核对框架

### 第 0 层：30 秒摘要

一句话写清目标用户、触发时点、要完成的业务结果、本次范围与非范围，并列出当前证据状态：需求已确认、代码已实现、已联调、已测试、已发布、生产已观察。各状态不能互相替代。

### 第 1 层：业务旅程与新旧分流

用 3—7 步说明“谁 → 从哪进入 → 看见什么 → 做什么 → 系统发生什么 → 成功或失败后去哪”。新旧流程使用四列：`场景 / 保持不变 / 本次变化 / 防串场措施`。跨 H5、PC、后端或外部系统时，明确每一步责任。

### 第 2 层：领域模型

定义术语、核心实体、唯一标识、实体关系、关键状态与转换条件。每个关键数量、金额、组织、状态或版本回答：从哪来、谁能写、谁能解释、冲突听谁的、多久有效。页面显示值、缓存副本、计算值与权威值必须区分。

### 第 3 层：异常、权限与可靠性

对业务拒绝、空结果、超时、重复提交、部分成功、并发修改、过期版本和跨系统不一致逐项判适用性，不适用时记简短理由；适用项按风险选择所需证据，不能为少讲而跳过必要验证。每条需展开的异常按 `触发条件 → 系统真实状态 → 用户看到什么 → 用户下一步 → 谁负责恢复` 描述；权限、幂等、事务、补偿与人工兜底只展开与当前操作有关的边界。不要求全部异常授课：正常空列表查询可仅展开空态与数据来源；付款写入应展开相称的未知终态、重试与恢复边界。

### 第 4 层：实现映射

再列页面、路由、入口条件、接口顺序、字段、表、权限校验位置和环境开关。每个字段按“业务含义 → 产生位置 → 消费位置 → 缺失或冲突行为”解释，并链接到前述业务节点。字段名不能代替业务名词。

### 第 5 层：验收与证据

建立 `业务承诺 → 页面状态/用户动作 → 代码落点 → 请求契约 → 验证证据 → 结论` 映射。设计、代码静态检查、构建、浏览器、Mock、真实接口、测试环境闭环与生产观察分别记录；结论使用 `通过 / 部分 / 未执行 / 受阻 / 未知`。

## 三岗位责任

### 林知夏 · 目标规划官（Product Manager）

- 对目标、角色、业务主线、实体关系、数据权威、状态、权限、失败恢复、范围和验收口径负责；
- 用“用户看到或操作 / 业务上发生什么 / 哪个系统负责”三列建立业务与系统的共同语言；
- 关键项未知时写 `unknown + 责任人 + 补证动作`，不能让接口清单掩盖业务缺口；
- 补足必要事实后组织独立解释，首次短诊断不计失败；不以“已读”“没有继续提问”或“代码已完成”判定理解。

### 周启明 · 体验工程官（Frontend Engineer）

- 编码前按首次最小说明输出一页“业务—页面—请求”图，其余角色/入口/出口、新旧分流、请求责任与证据在内部核对后按适用风险展开；
- 用读者熟悉的页面、交互、请求和状态管理作为入口，再映射到业务实体、数据权威和后端约束；
- 分开前端可见状态/请求归属与服务端权限、幂等、事务、副作用；路由参数、按钮禁用或前端过滤不构成安全与业务终态证据；
- 实现后提交业务—代码—请求—验证映射，不用笼统“已完成”概括。

### 陆行远 · 可靠服务官（Backend Engineer）

- 在 DTO、字段和接口之前说明核心实体、状态机、系统边界与数据权威；
- 对每个写操作内部核对业务键、权限、前置状态、幂等、事务边界、失败结果、重试/补偿、终态查询和审计的适用性；首次面向用户只展开当前关键状态、权威与一个重要失败，其余随风险与提问展开；
- 明确缓存、同步副本、请求上下文与最终业务事实的区别，不能用局部字段推导最终归属；
- 将事实、合理推断、待确认和已废止规则分开，代码现状不能自动证明需求正确。

## 案例改写示范

不采用：

> 先向 Meteorite 获取当前领料上下文，然后缓存 businessScene、repairContextVersion、cityCode、companyOrgCode、orderBelongOrgCode。

采用：

> 用户从维修工单进入领料前，H5 先请求 Meteorite 获取“本次操作属于哪个业务场景、当前上下文版本和可见材料范围”。这些信息用于后续页面分流、列表查询和提交校验，不代表 H5 自己决定最终采购公司。`companyOrgCode` 只限定用户能看见哪些材料；最终采购公司必须由另一个明确的权威规则或系统确定，当前资料未说明时保持 `unknown`。如果返回 `materialDetailList=[]`，表示请求成功但当前没有可展示材料，应进入正常空态，不按接口错误处理。字段的精确类型、缓存键与过期行为在接口契约章节说明。

该改写只澄清已给出的语义关系；没有资料支持的“最终采购公司由谁决定”仍保留为 `unknown`，不能擅自补全。

## 暂停编码的信号

- 一次纠正会改变角色、入口、主旅程、新旧分流、数据来源或写请求责任；
- 权限、数据来源、版本、幂等或失败恢复未知，且影响提交、取消、付款、对账等高风险操作；
- 新分支触发旧接口或污染旧状态，无法解释旧场景为何不受影响；
- 视觉、Mock、构建或前端字段被用来证明接口、权限或业务终态；
- 代码不能映射回明确的业务规则和验收；
- 同一流程连续出现两次局部纠正。

暂停后一次性给出当前旅程、新旧差异、事实/推断/未知/冲突、未知会影响的代码与验收，以及推荐答案与集中确认项。

## 理解门槛与培训嵌入

理解验证嵌入现有学习时段，不新增课程：

- D0：短诊断不计失败 → 补足必要领域事实/完整最小例 → 用户关闭文档与 AI 答案解释目标、主流程、实体/状态、一个失败结果及证据；
- D+2/D+3：从空白重建并保留首次错误、提示层级与修订原因；
- D+7：只改变一个未见条件，先预测受影响环节，再选择最小验证。

用户能够用自己的话串起“人—事—状态—结果”，本题必需维度已观察、预先指定的本题必需因果关系均已覆盖、无预先指定的关键因果错误，且关键未知有合理处置，才视为该题理解通过。已补足事实后，答案仍遗漏任何必需因果关系时，相应维度记“部分”、本题记“待补证”；补齐前不能判理解通过，不能仅凭没有相反结论放行。缺业务事实先补需求，已提供事实仍无法解释才定位学习卡点。AI 或员工生成的任务卡、代码和测试不计为用户能力；只有用户本人可归属的解释、判断、改写、运行或未见迁移才形成相应证据，并注明帮助程度。

复用现有证据卡，按 `USER_CAPABILITY_ASSESSMENT.md` 的“目标/主线、状态与权威、失败结果、未知处置、验证选择”五维，分别记 `正确 / 部分 / 错误 / 未观察`，不设总分。正确须覆盖本题必需因果；部分指遗漏必需关系；错误指与已给事实或关键因果矛盾；未观察须注明未作答、事实缺失或不适用。出题前冻结本题必需因果关系和关键错误，非关键扩展信息不列为必需，不要求所有任务完整考察五维。分维保留初答、修订、核心语义由谁提出和提示来源：独立 `independent`、无方向提醒 `light_prompt`、核心关系/机制/方案提示 `guided`、给答案后复述 `reproduced`、他人完成 `ai_or_employee_done`。语法/API 检索另记，不与核心方案提示混同。

D0 以实际学习发生日计，间隔按表现调整，固定日期不是完成证据。核心误解先缩小切片与纠错，再安排迁移；跨周期 D+7 保持 `pending` 并替换下一周期已有复盘内容，不加时补清单。10+3+1 仅为预算上限，最优性及实际负担仍为 `unknown`。

## 三任务试行与复核

从真实队列选择三个同一任务族、系统/实体数、风险和失败分支相近的任务（当前任务待选），不能直接把 token、可观测性与 RabbitMQ 三周主题当可比样本。记录：

- 首次说明前的领域熟悉度、已见材料与事实完整度；补足事实后的五维首次状态、预先指定的关键错误、提示来源及理解门槛首次通过时点；
- 首次正确主线的形成时间和用户用于补讲、纠错的实际分钟；
- 数据权威、状态与失败路径的遗漏数；
- 因违反已确认业务规则产生的返工轮次；新增范围另记，不混为返工；
- 首次报验时具有相称证据的必需验收项比例；
- 实现后新增的业务规则数量与严重逃逸缺陷；
- 用户实际投入、导师说明与额外文档的实际分钟，暂停/移出内容及真实反例；无法测量写 `unknown`。

三个任务结束后只校准标准和适用范围，不凭同向变化直接声称因果提效或稳定能力；最多支持限定任务族与条件下对下一同类任务的初步预测，后续对照真实结果。一次真实项目验收只确认该次范围。出现高风险反例时立即复核；没有可比真实任务时效果保持 `unknown`。

## 采用、拒绝与边界

- 采用：跨端、跨系统、陌生业务或可靠性相关需求，先建主线和业务模型，再写契约；实现后做映射与复述验收。
- 拒绝：先讨论字段、路由、序列化和组件，编码后再逐步发现登录态、查询阶段、数据来源与旧流程串场问题。
- 拒绝：把短诊断当未教事实的准入考试，或每个需求都讲完六层、九段及全部异常才继续工作。
- 边界：纯文案、颜色或已共享上下文的单点机械修改无需全套模板；分层说明不降低技术准确性，也不要求所有编码前都等待用户逐项确认；业务、接口与生产事实仍须对应事实所有者和真实环境证据确认。
