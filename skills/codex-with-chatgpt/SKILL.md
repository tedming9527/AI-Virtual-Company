# codex-with-chatgpt — 编排层 C2C 协作

## 心智模型（一句话）
员工 = 谁负责；执行者 = 谁动手；codex-with-chatgpt = 怎么让高手参与复杂任务；jev-use = 怎么做可靠判断；Chief of Staff = 谁来决定以上这些。

## 何时调用（C2C 触发，满足其一即可）
- 跨多个模块
- 架构设计
- 疑难 Debug
- 大范围重构
- 需要 PLAN → EXECUTE → REVIEW
- 首次执行风险较高

## 何时不调用（成本门禁，硬约束）
能单个执行者直接完成的，**绝不启动 C2C**：
- 改一个变量名 / 修一个 CSS / 增加一个字段
- 执行已有测试 / 格式化代码
- 简单 CRUD / DTO / Mapper / API 字段修改

C2C 会增加时间与 token 消耗；只有复杂度足够时才值得启动。优先级：**能直接完成，就不启动 C2C**。

## 协作循环（默认最多 2 个 Review Cycle）
```
PLAN → EXECUTE → REVIEW → FIX → FINAL REVIEW
```
- PLAN / REVIEW / 收口判断：由"规划·评审角色"（高能力推理/高手）承担
- EXECUTE / FIX：由执行角色承担
- 第 2 轮 FINAL REVIEW 仍不通过 → **BLOCKED** → 升级 Chief of Staff → 决定：继续 / 换方案 / 找用户
- 目的：控制 token 与执行时间，禁止 ChatGPT→Codex 无限来回。

## 与 jev-use 组合（互补，不竞争）
```
ChatGPT(规划)
  → jev-use(必要时判断方案/风险)
  → Codex(执行)
  → 测试输出
  → jev-use(判断是否通过)
  → ChatGPT(Review)
  → DONE / REPLAN
```
- **jev 负责**：风险 Gate、build/测试是否成功、多方案结构化判定、命令执行前 Gate
- **C2C 负责**：复杂任务的规划—执行—评审循环
- 总则：**jev 判断，C2C 协作，执行者执行，员工提供专业能力。**

## 本环境角色映射（Doubao）
无独立 ChatGPT/Codex 引擎时，按角色职责映射到实际可用执行者：
- 规划 / Review 角色 → 编排层 / 子智能体（高能力推理）
- 执行角色 → 执行子智能体
- jev-use → 判断门（已安装的判断型 CLI）
跨平台运行同理：以角色职责为准，映射到对应平台可用的执行者。

## 节点缺失回退与短时缓存（2026-09-24）
任一节点（C2C 的规划/执行角色、jev-use）缺失时，员工照常工作：按"本环境角色映射"退回单执行者直做 + 编排层自任规划/评审位；判断回到编排层/员工自判。节点是**加速器，不是依赖**；效率来自流程而非节点名。

三层分层（防"单次失败即写缺失"）：
| 层 | 决定什么 | 规则 |
|---|---|---|
| 瞬时探测 | 这次要不要重试 | 退避 + 失败计数 |
| 确认 | 要不要写"缺失" | 达阈值才写共享状态 |
| TTL | 多久忘掉再查 | 会话/窗口，防永久 |

防偶发确认（hysteresis）：
- **首错不写**：单次失败按网络抖动/超时处理，只退避，**不写状态**。
- **退避序列**：`1s → 5s → 30s → 2min → 5min`（封顶 5min）；失败递增等待，**任何成功即清零**并回 healthy。
- **确认阈值**：**连续失败 ≥ 3 次**（或滚动 30 分钟窗口内集中 ≥ 3 次）才把状态翻为 `missing` 并写入共享状态；避免稀疏抖动被误判为永久缺失。
- **回恢优先**：中途任一成功 → 计数清零、状态回 healthy（不必等 TTL）。
- **本地存在性检查**（如 `command -v jev-use`）是确定性的，**豁免退避与阈值**，一次判定即可；滞后确认仅用于远程/网络探测（平台节点、远程判断后端）。
- 即使已确认 `missing`，TTL（会话/约 15–30 分钟）仍强制周期重探，防"永久"。

共享状态（不各自重试）：节点缺失/可用性是环境事实，记在 `platforms/REGISTRY.md` 的 `node_status` / `last_checked`，所有员工读同一份；谁探到谁写（带时间戳，last-write-wins）。**不得**把节点可用性写入个人 MEMORY.md。
一句话：退避防抖动，阈值防误判，TTL 防永久，成功即回恢，本地一次判，共享不重试。

## 员工学习边界（只学三件事，不要求通读全实现）
1. **什么时候调用**（见"何时调用"）
2. **什么时候不要调用**（见"何时不调用"）
3. **怎么和 jev 组合**（见"与 jev-use 组合"）
按各自岗位命中触发场景时，定向使用本编排契约；岗位只记录自己相关的调用场景。

## 治理边界（任务治理优先，2026-09-24）
C2C 只是**执行通道**，不替代公司任务治理，也不构成任何豁免：
- C2C 执行的任务仍按 `TASK_LIFECYCLE.md` / `DELIVERY_POLICY.md` 分级登记（S/M/L）、留证据、走收口（`TASK_CLOSEOUT`）。
- 任务先按 `ROUTER.md` 完成进料与指派（owner + consult）后才进入执行通道选择；C2C 只替换"谁动手、怎么判断、几轮评审"。
- consult 状态只认实际交接（`none/proposed/declined/contributed`），C2C 内多个角色参与不等于"已协作/已评审"。
- 用户能力交接按 `ROUTER.md` 2026-09-18 规则执行，不因走 C2C 而省略。
- C2C 的 BLOCKED 升级即公司协作契约的升级路径（`COMPANY.md` 规则 13）。
