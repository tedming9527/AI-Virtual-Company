# 19 · 新人工作流改造蓝图

> 状态：2026-10-16 立项（设计蓝本，未实现/未安装）。
> 本页把"新人第一天上手"的完整工作流整合为单一改造基准；所有场景映射到平台**已有机制**，原则是**零新增平台功能，只做配置 + 交互 + 保护线**。
> 用户原始场景描述与"映射到现有机制/改造判断"分开记录，不混淆。
>
> **演进登记（2026-10-16）**：S1–S6 之后，对话迭代确认了本系统的治理能力定稿（初始化包+凭证、会话反向注册、规则强制注册门禁、三层规则生命周期、可视化工作台替代命令行），并据此与 WorkBuddy 做了差异化定位——见第七节。第一节"S1–S6"为初版交互（对话式/命令行），后续已明确升级为**可视化工作台（勾选/表单/看板），反对命令行**。

---

## 一、定位与价值主张

平台现状：工程已近完备（v1.10.0、18 份设计文档），但**价值闭环未跑通**——没有真实内容被喂进系统，最新功能（docs/18 本地实时监控）未发布未安装。

本次改造方向：**聚焦真实内容，把已建成的机制真正用起来**，不再新增平台功能。

核心判断（承接"剔除大模型能力后还剩什么"）：

- 能被大模型可靠替代的能力（语义推荐、评分、知识提炼、写卡、总结、检索摘要、全景渲染）——**交给模型**；
- 只能由确定性骨架承担的（版本账本、hash 绑定、schema 门禁、个人数据隔离、跨设备一致性、触发与后台调度）——**保留为薄约束层**；
- 真正的剩余价值 = **薄骨架 ＋ 真实知识内容**。本蓝图聚焦后者。

三大原则：

1. **能交给模型的，交给模型**——平台收敛为"薄约束层"。
2. **临时/私有与项目/中央严格隔离**——个人数据不入仓库（AGENTS.md 规约）。
3. **每个关键写操作保留人审门**——自动推进，但合并/部署等写操作须人审放行。

---

## 二、目标用户与场景清单

目标用户：新人（如"小明"）第一天上手，能力水平低于老手，需要规则约束、项目学习、受控开发、私有资产保护。

| # | 场景 | 用户输入 | 一句话 |
|---|---|---|---|
| S1 | 规则约束 | `/ted setRules` | 按通用/公司/项目三级勾选规则，注入本次对话 |
| S2 | 需求开发自动化 | `/ted pre-code` | 监听→分析→方案→人审→执行→合并部署→有界循环 |
| S3 | 读项目 + 临时知识 | `/ted docs` | 上传产品文档→本地临时知识库（本次参考，不入项目） |
| S4 | 新人学习 | `/ted docs` | 生成初级项目解说文档，落个人 learning/ |
| S5 | 私有资产 | 本地存留 | 对项目的特殊理解 = 私人小金库，本地私有、永不外传 |
| S6 | 任务勾选加载 | 开发任务中勾选 | 勾选本次重点参考，AI 受控自动加载 |

这六个场景构成一个完整闭环：**规则定边界 → 读项目/建临时库/学项目 → 攒私有小金库 → 任务开发（勾选加载 + 自动化工作流）**。它首次把"AI-Virtual-Company 的公司隐喻"激活：Agent 是员工，命令是上岗工具，规则、知识、开发流各管一段。

## 三、命令与交互设计

### 3.1 `/ted setRules` —— 三级规则注入（S1）

**交互**：对话式清单（非弹窗）。模型在对话中列出三级规则，用户用文字回复勾选（"选 1、5、7" / "全选"），确认后注入本次对话。

> 说明：原场景为"弹出可勾选页面"，但该能力依赖宿主交互卡片，平台无法保证。**首版降级为对话式清单**，宿主支持交互卡片后再升级。

**三级规则与落点**：

| 等级 | 示例 | 落点 |
|---|---|---|
| 通用业界最佳实践 | 最小改动原则 | `rules/`（跨包全局，已有） |
| 公司约束 | 不能提交密码 | `packs/framework/company/policies/`（已有） |
| 项目约束 | 生产分支 master_txc；git 凭据按目录取配置 | 项目 AGENTS/目录级（已有） |

**生效边界（关键）**：

- **首版：仅本次对话生效**——按等级把勾选规则注入会话上下文（`additionalContext`，docs/11 已有注入机制），**不写库、零持久化、零配置边界风险**。
- 写库版（保存为默认规则）：属配置写操作，触及边界。通用规则改 `rules/` 是改中央仓库内容，须人审/PR；公司/项目约束落部署层或个人目录。**不在首版范围**。

### 3.2 `/ted docs` —— 读项目、建临时知识库、学习（S3/S4）

**交互**：`/ted docs` → AI 打开项目文档 → 用户上传产品文档 → AI 分析 → 生成本地临时知识库 + 项目解说。

**产物分流（都不入项目）**：

| 产物 | 内容 | 落点 | 生命周期 |
|---|---|---|---|
| 临时知识库 | 产品文档分析出的参考要点 | 本地（非 iCloud） | **待定**：随本次开发闭环结束清理，或设保留期 |
| 学习产物（初级解说） | 项目架构 + 初级解说文档，按能力分级 | 个人 `learning/` | 可保留（个人学习资产） |

**能力分级**：项目解说文档按用户能力水平生成（初级/进阶），是模型按难度生成的学习产物，属个人 `learning/`，不入项目。

### 3.3 `/ted pre-code` —— 需求开发自动化工作流（S2）

**原场景流程**：设置监听 → 结合监听分析需求/他人进度并调整方案 → 方案草稿-人工审核 → 审核完成自动执行 → 自动合并部署测试环境 → 1-4 自动循环。

**收敛后的流程（红色为相对原场景的修正）**：

```
① 设置监听（cron 定时器）
   · 需求/bug issue 关键字监听
   · 关键他人协作项目代码与部署监听（需数据源接入与授权）
→ ② 结合监听分析需求与进度，产出方案草稿（模型）
→ ③ 发审核通知（飞书邮箱）→ ⏸ 等确认回执（通过/拒绝）
→ ④ 审核通过后执行方案动作（模型）
→ ⑤ 合并/部署：自动准备 PR + 人审放行后才合并部署测试环境
→ ⑥ 复盘 → 回 ①（有界循环：每个需求闭环跑一轮，或最多 N 轮且每轮过审核门）
```

**两条必须守的修正**：

1. **自动合并部署 → 人审放行**：AGENTS.md 明确"特性分支 PR 经人审合并 master"，自动合并违规。首版为"自动创建 PR + 人审确认后合并部署测试环境"；生产部署不在自动范围。
2. **无界自动循环 → 有界**：平台已有自动委派失控教训（docs/16，模型额外委派/活动子任务）。自动循环必须有终止条件（每需求一轮 / 最多 N 轮 / 每轮过审核门），防止无限执行与重复部署。

**审核回执（关键）**：通知是单向"发出"，要构成审核闭环必须配套"确认回执接收"——系统等到通过/拒绝回执才进入下一步，**未回执则停在审核门，不自动继续**。审核渠道首版定**飞书邮箱**（lark-mail）。

### 3.4 任务勾选加载 —— load_asset（S6）

**交互**：每次特殊开发任务，用户勾选本次重点参考（知识卡/临时库/小金库）→ 确认后 AI 受控加载。

**加载纪律（映射 docs/11 load_asset 机制）**：

```
勾选（声明 requiredAssets）→ 任务绑定 → 摘要预载（summary+章节游标，不全文塞入）
→ 按需分块读正文（游标/预算约束）→ 开发产出（使用可追踪 docs/12）
```

关键：**先摘要、后正文；按需分块、用完即止；受会话字节预算约束**（docs/11，会话累计 262144 字节），防止上下文爆炸。勾选小金库资料 = 本地加载辅助开发，产出物不引用原文进项目。

## 四、资产分层与保护线

| 层 | 内容 | 去向 | 边界 |
|---|---|---|---|
| ① 通用知识 | 可分享的后端知识卡、技能包 | 可走候选→复核→转正，进中央/全景图 | 可发布 |
| ② 项目/公司知识 | 项目约束、架构、临时参考 | 只在本项目/本会话生效 | 限范围 |
| ③ 私人小金库 | 对项目的特殊理解、踩坑、竞争资产 | 只存个人本地（非 iCloud） | **本地私有·绝不外传** |

**小金库两条保护线**：

1. **防泄露**——小金库内容不进仓库、不进全景图、不进任何交付物（硬规则锁死）。
2. **不误转正**——小金库是"个人竞争资产"，不是"通用模板"，**永不自动进入候选/转正链路**。

> 依据：AGENTS.md 已定义"客户端独有资料"（初始化后保持未升级身份）；docs/08 个人目录规约（个人数据不入仓库）；双向流转中反向升级须经评审。小金库是把这既有资产类别命名为"竞争资产"。

## 六、待定项与验证标准

### 待定项

| 项 | 现状 | 需决定 |
|---|---|---|
| 临时资料生命周期 | 未定 | 保留多久？开发闭环结束是否自动清理？（参考 docs/18 的 24h 滚动保留 + 非 iCloud 落点） |
| 审核回执实现 | 定飞书邮箱 | 邮件"通过/拒绝"链接的具体交互与回执校验 |
| 宿主 UI | 降级为对话式清单 | 后续是否升级交互卡片（宿主能力） |
| 合并部署人审放行 | 首版人审 | 合并/部署动作的授权与审计落点 |
| 他人协作项目监听 | 需数据源 | 监听渠道（GitHub webhook/轮询）、权限边界与授权 |

### 验证标准

- 每个命令在真实对话中可触发，交互流与预期一致；
- 临时/私有资料在仓库、全景图、交付物中**不可见**（防泄露验证）；
- 小金库资料**不进入候选/转正链路**（不误转正验证）；
- pre-code 审核未回执时流程停在审核门，不自动继续；
- 自动循环有界（每需求一轮 / 最多 N 轮 / 每轮过门）；
- 合并/部署动作须人审放行记录，生产部署不在自动范围。

## 七、与 WorkBuddy 的差异化定位（2026-10-16 增补）

> 本节回答"这套系统跟现在的 WorkBuddy 有什么区别"。WorkBuddy 的能力描述来自其官方文档 / 腾讯云公开资料（来源见本页附），非凭记忆断言。

### 7.1 WorkBuddy 是什么

WorkBuddy 是**腾讯出品**的全场景 AI 办公工作台（企业级 Agent 客户端）：自然语言描述需求 → 自主规划执行 → 交付文档/表格/PPT 等完整成果；拥有 100+ 专家、可调 Skills、知识库、多平台接入；提供项目级配置（指令/规则、连接器、专家、技能），任务自动从项目配置拉取信息注入上下文；有 Agent 模式（直接执行）与 Plan 模式（先规划等确认）；已接入企业微信侧边栏（企微 5.0.12）。

### 7.2 相似点（诚实承认 WorkBuddy 已有雏形）

| 维度 | WorkBuddy 已有 |
|---|---|
| 项目配置注入规则到任务上下文 | ✅（项目"指令"，任务自动继承） |
| 外部服务连接 | ✅（连接器） |
| 专家 / 技能 / 知识库 | ✅ |
| 先规划等确认的审核模式 | ✅（Plan 模式） |

### 7.3 本质区别（重点）

| 维度 | WorkBuddy（腾讯） | 本系统（Ted 工作台） |
|---|---|---|
| **产品形态** | 商业化 SaaS，绑定企微生态，别人搭好即用 | 自建、独立，**可切换 AI 引擎、不锁供应商** |
| **规则治理深度** | 项目级一次性指令 + 任务自动继承（无生命周期、无门禁、无 AI 自定规则审核） | **三级规则生命周期 + 规则强制注册门禁 + 来源标注 + AI 自定规则可审 + 归档清理** |
| **上下文治理** | 项目配置自动注入（较粗粒度） | **初始化包+凭证复用 · 会话反向注册 · 业务跨项目裁剪注入 · 预算约束** |
| **隐私自主** | 云端 SaaS，数据在腾讯云，强绑企微 | **小金库本地私有 · 凭据入个人本地不入库 · 数据完全自持** |
| **可信度哲学** | **信 AI**——帮你自主执行并交付成果 | **管 AI**——确定性门禁 / 审计 / 去主观化 |
| **深度场景** | 通用办公（文档/表格/PPT/研究） | 深度开发 + 业务知识治理（代码=权威源、踩坑沉淀、业务跨项目） |

### 7.4 结论

WorkBuddy 的差异化在**"执行与交付"**（开箱即用、成果导向）；本系统的差异化在**"规则治理与隐私内核"**（管理 AI、数据自主、确定性审计）——后者是绑定企微生态的商业 SaaS 难以做到、且与其"信任 AI 自主执行"哲学相悖的部分。

因此二者**非同类替代，而是互补定位**：WorkBuddy 是通用执行层，本系统是**治理控制层**。本系统甚至可反过来作为"给任何 Agent（含 WorkBuddy）套一层规则治理与隐私外壳"，正契合本项目双核定义——**公司的规则注入 + 给个人的技能保留隐私的地方**。
