# ted-avc-manager：执行介入架构

## 要解决的问题

目录扫描、版本更新、全景图和回答署名只能证明资产存在、更新发生或输出格式被检查。要证明中介层参与执行，还必须有可关联的任务建立、实际上下文交付、工具调用前判断、调用后事实和产物核对。不得把署名 Hook 成功替代执行监督验收。

本版本增加项目级原生 Hook 执行适配器与 MCP 任务协议。引擎版本 `engineVersion` 与中央资产目录版本 `catalogVersion` 分开记录：升级管理器不代表所有项目资产已升级，也不要求改写仍运行旧资产的项目。角色展示读取专业包的“中文名字·职业”；角色 ID 只用于路由。逻辑任务主责与 `platform agent` 实际执行者分别记录。

## 四个层次

| 层次 | 输入与职责 | 生效证据 | 当前边界 |
| --- | --- | --- | --- |
| 资产层 | 通用包、个人原创包、外部候选、已安装资产；登记来源、版本与摘要 | 目录扫描、登记记录及真实文档 SHA | 发现或安装不能直接认定已纳管、已加载 |
| 上下文层 | 选定角色 PROFILE、显式技能/知识/框架文档 | MCP 返回全文，任务固定文档与 metadata 摘要 | 无法证明模型已经理解或遵守全文 |
| 执行层 | 原生会话/回合绑定、工具名单、外层调用次数预算 | PreToolUse 实际准入或拒绝，PostToolUse 可见事实 | 只覆盖宿主触发的 Hook，不是模型请求网关 |
| 交付层 | 原始事实分类、产物文件、版本、主责与执行者 | 工具完成摘要、产物 SHA、署名 Stop 回执 | 文件存在和格式合格不代表业务正确或全面监督 |

中央全景图展示通用资产及可验证的上游候选 PR；本地全景图叠加个人目录、自定义资产与执行回执，并显式展示来源和治理状态。个人正文、路径与执行记录不能进入公开产物；候选 PR 也不能冒充已经发布的资产版本。

## 原生执行流程

1. 署名适配器在 `UserPromptSubmit` 建立真实 `session_id / turn_id / receipt`。执行适配器读取同一回合回执，向宿主注入绑定字段和 `task_begin` 指令；不能接受模型随意填写的“执行成功”标记。
2. 未建立任务前，普通流程只允许部署配置中逐项列出的管理器自省、加载与 `task_begin` 工具名。固定只读自检、用户明确授权的受限维护另走下述独立入口，没有通配符或“任意工具启动豁免”。其他工具在 `enforce` 中被拒绝，在 `monitor` 中记录未绑定事实并放行。
3. `task_begin` 校验原生回执与部署允许的角色，读取实际 PROFILE 全文，固定角色版本、中文展示名、metadata/PROFILE SHA、中央目录版本及 metadata 目录摘要。一个原生回合只有一个任务 ID；重复建立可查询原记录，但不能在同一回合扩大名单或预算。
4. 任务执行前，`PreToolUse` 校验任务仍活动、工具在精确名单中、预算未用尽、已固定的角色/目录/已加载资产未漂移。按宿主 `tool_use_id` 预留一次。相同的待完成调用可幂等重试；不同输入复用 ID 或已完成 ID 再执行会被拒绝。
5. `PostToolUse` 只写可见返回的 SHA，明确退出码来自哪个可见字段。没有退出码就是 `unknown`，没有响应字段就是未知完成事实；不能从“Hook 没报错”推定工具执行成功。重复 Post 不覆盖首次观察。
6. `task_closeout` 要求每次预留都有可见完成或明确的未知分类，并读取实际输出文件核对 SHA。未观察到的调用必须通过 `unknownCalls` 逐项注明原因。关闭任务后 `enforce` 不再允许执行工具。结束回复还由独立署名 Stop 校验，两个验收结果分开呈现。

`task_closeout` 是显式列入名单的控制调用，单独记账而不消耗执行调用预算，避免最后一次预算用尽后无法关闭任务；它不提供执行任何命令的能力。已发现资产漂移时仍允许关闭活动任务，关闭回执明确标记 `integrity: invalidated`，避免把损坏任务悬挂或冒充正常验收。控制调用返回由 MCP 提供，不冒充被观察到的外部工具完成。

## 会话恢复与回合回执

宿主事件字段按 [OpenAI 官方 Hook 文档](https://learn.chatgpt.com/docs/hooks) 核对；以下回执状态属于本项目的适配器契约。

`SessionStart` 只注入项目范围、岗位展示与回合使用规则，不签发末尾回执，也不创建或改写 turn 状态。它可能在 UserPromptSubmit 之后因恢复或压缩再次触发，不能让后到的启动提示覆盖当前回合编号。

`UserPromptSubmit` 必须携带真实 turn_id，签发并固定当前回合 nonce 与 `deliveryVersion`。`Stop` 只接受该回合的回执；没有 turn_id 时显式失败，不降级为 session 编号。跨回合回执标记为未验证；署名失败只告警，不强制纠错或续跑。

进行中的回合按最初注入的发布版本收口，适配器实际版本另记审计 `version`。升级不追写本回合署名；旧记录缺少 deliveryVersion 时，只从匹配 session/turn/receipt 的原生 UserPromptSubmit 审计恢复签发版本，不修改原始回执。新回合使用新发布版本。这保护升级中的输出一致性，不提供扩大活动任务工具合同或清除资产漂移的能力。

## 部署契约

执行适配器沿用署名部署文件的 `projects` 配置，不写机器路径到中央包。每个项目独立开关与模式：

```json
{
  "organization": "组织展示名称",
  "projects": [{
    "root": "/path/to/project",
    "roles": ["ai-engineer", "test-expert"],
    "execution": {
      "enabled": true,
      "mode": "monitor",
      "maxToolCalls": 40,
      "bootstrapTools": [
        "mcp__ted_avc_manager__list_packs",
        "mcp__ted_avc_manager__find_skill",
        "mcp__ted_avc_manager__load_asset",
        "mcp__ted_avc_manager__task_begin"
      ]
    }
  }]
}
```

安装函数 `installExecutionHooks(deploymentFile, codexHome)` 只登记 `UserPromptSubmit / PreToolUse / PostToolUse`，保留其他插件及署名 Hook，不修改原生信任状态。署名 UserPromptSubmit 必须先登记；实际宿主执行次序仍需原生验收。未绑定项目正常返回空输出。配置缺失、项目搬迁或解析失败时，只返回 `systemMessage` 告警并要求修复，不把未知配置推断成 enforce 或拒绝所有项目的工具。采集/存储异常在 monitor 和 enforce 下均只告警；monitor 绑定不可用时继续已授权任务。只有已确认的显式 enforce 合同拒绝或独立维护授权限制可以拒绝，平台沙箱、权限和审批继续有效。

### 监控工具审批配置

Hook 信任与 MCP 工具审批相互独立。`task_begin` 只登记目标和工具范围，不执行目标中描述的操作；`load_asset` 读取本地资产并记录加载；`task_closeout` 读取产物计算摘要并关闭记录。三者有本地写入，因此工具注解为 `readOnlyHint: false`、`destructiveHint: false`、`openWorldHint: false`。注解描述副作用，不替代用户授权或保证审批通过。

显式运行客户端安装/升级脚本 `scripts/update-local-client.py` 时，安装范围包括上述三项单工具默认批准。注册 MCP 后自动补齐；先保存再恢复已有工具策略，避免 `codex mcp add` 重写服务器配置时丢失用户选择。已有逐工具 `prompt` / `writes` / `auto` / `approve` 均保留，不修改全局审批、其他工具策略、启用列表或 Hook 信任。`init` 和单独安装 Hook 不修改这些审批设置。

已有客户端可独立安装（Python 3.11+，服务器须已注册）：

```sh
python3 scripts/install-codex-approvals.py --codex-home "${CODEX_HOME:-$HOME/.codex}" --check
python3 scripts/install-codex-approvals.py --codex-home "${CODEX_HOME:-$HOME/.codex}" --authorize-monitor-tools
```

默认目标是 `mcp_servers."ted-avc-manager".tools.<tool>.approval_mode`。不同服务器标识通过 `--server-id` 指定；确为插件提供且已存在该配置表时，加 `--plugin-id` 使用 `plugins.<plugin>.mcp_servers.<server>`，不同时配置两个命名空间。

安装器保留原文和注释，校验修改前后 TOML 语义，仅写所选工具。第一次有修改时，在客户端目录保存权限为 `0600` 的原配置备份，再原子替换；备份可能包含敏感配置，不能提交到仓库。重复运行不重复追加；异常 TOML、链接目标、并发安装锁或无法安全处理的内联表拒绝写入。输出 `preserved` 表示沿用已有选择，不能将其解释为已经自动批准。

配置格式以 [Codex 官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference) 为准。写盘后须重载客户端，在新会话核验调用；托管权限仍可能施加约束。允许任务登记不授权后续删除、Git 推送、网络访问或任意终端命令。

所有可执行入口固定为管理器的 Node 脚本；部署文件不含任意 shell 片段。允许工具时返回空输出，保留平台自己的权限、沙箱和审批规则；只有 `enforce` 拒绝返回原生 `permissionDecision: deny`。不自动跳过信任门禁，也不把 Hook 文件存在当作运行成功。

原 `pack-manager` 的工具名仅作为迁移兼容名称被接受；新配置与公开展示使用 `ted-avc-manager`。

## MCP 接口与存储

内部同步 API 位于 `mcp/ted-avc-manager/src/core/execution.js`；MCP 映射保持 snake_case 工具名，绑定参数为 camelCase。

| 工具 | 必需输入 | 返回与约束 |
| --- | --- | --- |
| `task_begin` | `sessionId, turnId, receipt, role, goal, allowedTools, maxToolCalls` | 固定任务记录与完整 `roleProfile`；预算不得高于部署上限 |
| `load_asset` | 绑定三字段及 `source, type, name`；可选包内文档相对路径 `entry` | 来源、版本、摘要及所选正文；活动任务登记上下文交付事实 |
| `task_closeout` | 绑定三字段、非空 `artifacts: [{path, sha256?}]`；可选 `unknownCalls: [{toolUseId, reason}]` | 真实产物 SHA、每次调用的 observed/unknown 分类与关闭任务记录 |

`source` 仅允许 `general` 和已登记 `local-custom`。通用资产从 `packs/<type>/<name>/` 读取。本地技能必须处于个人 `custom/`，具有唯一显式登记、当前 SKILL 与 meta 的组合 SHA 及版本匹配（组合摘要为 `sha256(entrySha256 + ':' + metaSha256)`）；只有正文摘要的旧登记需要重新复核登记。未登记、变更未复核、archive/staging、符号链接、路径穿越均拒绝。选择知识或框架正文不等于激活其中任何可执行程序。

产物只能位于当前项目或配置的个人 `deliverables/`，且必须是真实普通文件。运行记录位于仓库 `runtime/execution/tasks/<taskId>.json` 和 `runtime/execution/events.jsonl`。taskId 由项目真实路径、原生会话、回合和回执共同推导；不能靠另填 taskId 重置预算。每个任务以目录锁串行更新，JSON 先写新文件再原子替换；采集 Hook 遇到锁冲突只告警，显式管理接口请求可重试。目录/记录/产物符号链接被拒绝。

审计只存上下文/输入/响应摘要、工具名、时间、版本、状态和必要关联 ID，不保存完整提示、工具响应或凭据。任务文件包含部署根与实际产物路径，只留在本机 runtime，不进入中央提交或公开页面。PROFILE 全文只通过 MCP 返回，不复制到审计。

## 这层实际约束什么

任务的工具名单由执行者声明，部署上限约束调用次数、角色与启动工具；**它不是用户授权的替代品**。原生平台权限仍然生效。本实现按工具名准入并记录参数 SHA，不解析任意 shell 的语义，也没有逐参数/argv/cwd 规则。例如一个 Bash 调用内部可运行多个命令；code-mode 中的嵌套工具可能被宿主单独报告，计量以实际 Pre/Post 事件为准，不能外推为全部底层命令数。不能把预算数字宣传为底层命令数或模型请求数。

当前 Hook 与存储由本机用户控制，用户可以禁用适配器或改写本地文件。它提供本机项目范围的协作约束与事实链，**不是管理员不可绕过的安全边界**。不能管理宿主隐藏的模型选择、系统指令、token、成本、未暴露的子代理调用或未触发 Hook 的工具。上下文全文交付、工具准入、结果观察、署名验证和完整监督必须作为独立状态展示。

## 验收与后续演进

本模块回归覆盖真实文件系统与入口进程：nonce/原生回合匹配、不可扩大合同、未建任务拒绝、精确工具名单、次数上限、待完成调用幂等、已完成 ID 禁止复用、角色/通用文档/本地登记漂移、未知响应分类、产物 SHA、路径/锁异常、monitor 与 enforce 区别、原生 JSON 输出、保留其他 Hook 且不授予信任。反向拒绝用实际文件哨兵确认测试 harness 没有继续调用 handler；它仍不是宿主原生拒绝验收。

部署验收必须另外通过真实客户端完成：记录当前会话注入、成功调用与 Post；在独立受控项目中执行一项未授权工具与超预算调用，验证**真实 handler 的副作用没有发生**；将 monitor 原始记录与 enforce 拒绝记录一并归档。单元测试通过只能证明模块逻辑，Hook 安装只能证明配置写入。

后续按可验证边界逐步增加：

1. 从部署配置引入用户定义的工具/参数范围和预算策略，扩展批准后新任务的迁移协议，保持原生审批权。
2. 对平台确实支持的专用执行 handler 加入 typed argv/cwd 与产物契约，拒绝开放“任意 shell 网关”；校验拒绝发生在 handler 前。
3. 增加异常终态、取消/超时、陈旧锁恢复与 TTL 清理；当前进程崩溃可能留下锁或活动任务，不能自动当作成功关闭。
4. 只有平台提供真实模型请求入口时才增加 token/成本/模型选择政策；平台不可见的数值继续显示 unknown。
5. 将本地任务观察与资产来源、候选 PR、版本升级接入全景图，展示“发现 → 登记 → 上下文交付 → 原生介入 → 产物验收”的真实状态，分别记录成功、失败与未观察到的事实。

## 自检与受限维护入口

绑定工具本身不可用时，恢复不能再次依赖该工具。入口分两种：

- `maintenance-doctor [--deployment <file>]`：只读配置检查，不创建任务、回执或维护授权。输出配置状态及可精确调用的 `diagnosticCall`；宿主工具是否暴露、当前聊天是否绑定仍为 unknown。`PreToolUse` 精确接受此固定命令，`PostToolUse` 不触发普通任务/库存写入。即使部署 JSON 损坏或回执缺失，也能自检。
- `maintenance-open <input.json> --authorize-unbound-maintenance`：本地操作者依据用户明确授权开通有限操作；不暴露为 MCP 工具，不需要 task_begin 或 footer 回执。强制 Hook 已阻断代理时，从用户自己的终端调用这个独立入口；不能用“自检”关键词、伪造回执或全局放开 shell 解决。

固定自检只匹配原生 `exec_command` / `functions.exec_command`，使用当前 Node 与 CLI 的绝对路径、完整单条命令、相同工作目录、`shell: /bin/sh`、`login: false`。允许输出长度/等待时长参数；拒绝其他参数、追加命令、登录 shell、环境注入、权限升级与未知包装器。客户端若只报告外层编程工具，其内部调用不能推定已验证；需支持该原生接口或从操作者终端执行自检。返回结果从不包含 `permissionDecision: allow`，继续遵守平台审批和沙箱。

维护输入由本地操作员准备；以下是模板，真实 sessionId/turnId 必须取当前宿主事件，不得照抄示例，也不得把授权引用当成身份签名：

```json
{
  "sessionId": "<current-native-session>",
  "turnId": "<current-native-turn>",
  "userAuthorized": true,
  "reason": "task_begin_unavailable",
  "authorizationRef": "<reference to explicit user authorization>",
  "unavailableEvidence": "<current tools/list or connection failure evidence>",
  "ttlSeconds": 600,
  "operations": [{
    "purpose": "test",
    "tool": "functions.exec_command",
    "cwd": ".",
    "input": {"cmd": "node --test mcp/ted-avc-manager/src/core/execution.test.mjs"},
    "maxCalls": 1
  }]
}
```

`input` 必须与目标客户端的实际原生工具参数一致，包括命令、workdir 等字段；不解释自然语言意图，不默认批准 shell 任意输入。用途仅有 `initialization-read`、`connection-diagnosis`、`adapter-edit`、`test`。授权输入文件与运行数据留在部署侧 `runtime/`，不提交个人路径、完整提示或凭据。

维护契约固定项目真实路径、部署文件路径、会话、回合、操作工作目录与工具输入 SHA-256；JSON 对象键顺序不影响匹配。有效期最多 3600 秒，总预算最多 100 次。同一回合不能重开或扩大契约，已有绑定任务不能用维护刷新预算；追加授权需新的真实回合。准入按调用 ID 预留，待完成重试不重复计数，完成调用不能重放；过期、撤销、锁冲突、损坏及符号链接均不能获得维护放行。在 monitor 项目内，已开通维护契约的范围与预算也严格校验。

该入口依赖可读的项目部署范围，但不依赖岗位正文、库存扫描或 footer 回执。损坏的部署配置由操作者在 Hook 外修复。授权信任边界是当前用户控制的本地操作入口，`userAuthorized` 是显式声明，不是已验证用户身份；精确命令摘要也不等于对命令及其依赖脚本的沙箱隔离。操作者须审阅实际命令、修改目标和副作用，外部权限依然由宿主控制。

`maintenance-status <input.json>` 查询状态；`maintenance-close <input.json>` 撤销授权，两者只需 sessionId/turnId。维护记录及审计在 `runtime/execution/maintenance/`；事件注明 `unbound_maintenance` 与 `actualExecutor: platform agent`，只记录输入/响应摘要与实际可见退出码。迟到的 Post 仍保留为维护事实，缺失返回记 unknown，不覆写已观察结果。

恢复时使用当前真实 receipt 调用原有 `task_begin`。仅当原有回执、角色、契约校验通过且任务实际建立后，授权变为 `rebound` 并记录任务 ID，维护调用不会写入新任务的 calls。CLI 手工模拟 Hook、独立 MCP 握手成功、配置写入、已有聊天实际加载及真实回合绑定是不同证据；没有宿主回执时保持未绑定，绝不人为签发一张用于验收的“真实”回执。

验证：`node --test mcp/ted-avc-manager/src/core/execution.test.mjs mcp/ted-avc-manager/src/core/codex-hooks.test.mjs mcp/ted-avc-manager/src/core/server.test.mjs`，覆盖普通强制门禁、自检入口、注入/越界拒绝、授权/预算/时效、撤销、损坏、原生回执校验与重新绑定。

## 使用前正文门禁

部署 `requiredAssets` 与任务 `requiredAssets` 合并固定，例如 `general:skill:ted-avc-manager`。实际执行工具前须已有对应 bound load_asset 回执；只有模型自报不能通过。load_asset 与 task_closeout 是精确名单内的管理控制调用，单独记账且免执行预算，避免加载/收口死锁。可配置部署 allowedTools 限制任务可声明的工具集合；仍保留原生用户授权与沙箱。

## 发布后本地升级

`python3 scripts/update-local-client.py vX.Y.Z --node <Node22>` 从 origin 拉取精确发布 tag，要求工作树干净且只允许 fast-forward，按版本独立安装库，登记新 MCP、桥接技能和 Hook。不清理个人数据。原生 API 审阅并信任精确 Hook 定义后，reload MCP、刷新 skills/list，并重新执行原生验收。既有旧版管理器的已知原生 Hook 入口可在保留原件与哈希后转发新版本；这解决旧会话缓存的 Hook 命令，新执行事件仍需原生客户端重新加载才算启用。本项目默认 monitor，enforce 在明确绑定的隔离验收项目中测试。

当前客户端更新脚本仍属于旧版安装流程，不满足新的全量重建要求。用户数据初始化、客户端全量重建、清理前保全和第二步导入按 [14 · 客户端初始化重建设计](14-客户端初始化重建设计.md) 分离实施；不得将旧脚本执行成功宣称为新初始化验收通过。
