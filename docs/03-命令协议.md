# 03 · 命令协议

> 用户以自然语言触发，Agent 自动识别并执行预定义流程。
> 核心：**识别要分层，不能靠大模型自由发挥**。

## 1. 语法

```
github://owner/repo[@branch|@tag]  +  动作词
```

## 2. 动作词表（可扩展，覆盖「后续流程指令」）

| 动作词 | 触发的流程 |
|---|---|
| 初始化 / 安装mcp | fetch 仓库 → 读 bootstrap.json → 装声明的 MCP → 加载 packs/rules/记忆 → 就绪 |
| 升级 | check_update → 版本对比 → 增量应用 |
| 检查 / 检查更新 | dry-run：只汇报版本差异，不动 |
| 同步 | 回传日志 / 晋升申请 |
| 生成全景图 | 扫描目录规约 → 聚合元数据 → 渲染 HTML（可发布或仅本地） |
| 体检 / doctor | 校验个人目录规约（缺失/多余/命名/哈希），只报告与授权修复 |
| 配置 / config | 合并 preset/custom 展示生效配置，逐项标注来源 |
| 导入 / import-scan | 外部资产进 staging → 自动打标 + 台账，待人工复核 |
| 绑定 / bind | 绑定项目到个人目录（注册 manifest + 创建项目骨架） |

## 3. 三层解析机制

```
用户输入："根据github://xxx，开始执行初始化，安装mcp"
        │
        ▼
① URI 解析层（确定性代码，正则）
   → 抽出 owner/repo、branch/tag —— 不交给 LLM 猜
        │
        ▼
② 意图映射层（关键词表）
   "初始化/安装mcp" → init_flow；"升级" → upgrade_flow；...
        │
        ▼
③ 流程执行层（预定义 pipeline）
   init_flow 的步骤写死在代码/skill 里
        │
        ▼
④ LLM 执行 + 汇报（按步跑，结果反馈给用户）
```

## 4. 四条硬原则

1. **地址/版本解析是代码，不是 LLM 判断**——正则抽 URI，模型不能编造。
2. **流程步骤预定义**——LLM 是「照着流程执行的人」，不是「设计流程的人」。
3. **歧义/失败就停下问**——仓库不存在、tag 找不到、MCP 安装失败 → 明确报错等指示，不猜、不续跑。
4. **版本可见**——代理流程启用后，每次流程结束的**最终汇报语句必须带上当前生效版本号**（如「当前版本 v1.2.0」），让用户始终能识别在用版本。

## 5. 与 skill 机制的关系

本命令协议落成豆包 skill 模型：

- 一个 skill = 触发词 + 预定义流程；
- 「初始化」做成一个 skill：触发词含 github:// + 初始化/安装mcp → 命中后按 skill 流程跑；
- 「后续流程指令」（升级/检查/回传/生成全景图）做成同系列 skill，共用同一个 URI 解析层。

## 6. 示例

```
用户：根据 github://acme/ai-virtual-company，开始执行初始化，安装 mcp
Agent：
  ① 解析 → repo=acme/ai-virtual-company, tag=latest
  ② 映射 → init_flow
  ③ 执行 → clone → 读 bootstrap.json → 扫描目录规约 → 安装 mcp/pack-manager → 分层注入 → 就绪
  ④ 汇报 → 「初始化完成，已安装 pack-manager，加载 3 个技能包、2 个知识包。当前版本 v1.2.0」

用户：升级
Agent：check_update → v1.2.0 → v1.3.0（minor，兼容）→ 增量应用
       → 汇报 → 「升级完成，变更清单见下。当前版本 v1.3.0」
```
